                  XOF-based key schedules for TLS 1.3
                 draft-sullivan-tls-xof-schedule-latest

Abstract

   TLS 1.3 runs its entire key schedule on HKDF over SHA-2.  This
   document defines an extension that replaces that schedule with one
   built on an extendable-output function (XOF): the negotiated KDF
   governs every derivation, the Finished and binder MACs, and the
   transcript hash, so no SHA-2 remains in the key schedule.  The cipher
   suites, AEAD algorithms, state machine, and record layer are
   unchanged, and a connection without the extension uses HKDF as today.
   Two KDFs are defined, SHAKE256 and the reduced-round TurboSHAKE256.
   This document updates RFC 9258.

1.  Introduction

   In TLS 1.3 [RFC9846], every cipher suite runs its key schedule on
   HKDF over the suite's hash.  This document defines an extension that
   negotiates an XOF-based KDF for the connection.  Its key schedule
   runs on a single Keccak permutation and replaces HKDF across every
   derivation, the Finished and binder MACs, and the transcript hash.
   The permutation is the one a deployment already carries when it uses
   SHA-3, ML-KEM, or ML-DSA.  When no KDF is negotiated, the cipher
   suite's hash names HKDF and TLS 1.3's own schedule runs, exactly as
   today.  Instantiating HKDF with a SHA-3 hash would remove SHA-2
   without changing how the schedule works.  This document changes the
   schedule itself, not the hash.

   TLS 1.3 already negotiates groups, KEMs, signature schemes, PSKs, and
   AEAD algorithms.  This document extends that agility to the key
   schedule itself.  A TLS 1.3 cipher suite identifies an AEAD algorithm
   and the hash used with HKDF.  This document leaves the suite alone
   and negotiates the KDF beside it:

   connection = cipher suite (TLS 1.3) + KDF (this document)

                       Figure 1: Cipher Suite and KDF

   A KDF (Section 3) defines every key-schedule computation the
   connection uses: the transcript hash, the secret and key derivations,
   the Finished and PSK binder MACs, and the Encrypted Client Hello
   acceptance computations.  It is negotiated in the schedule_profile
   extension of Section 6, independently of the cipher suite.  A
   connection that negotiates no KDF is a TLS 1.3 connection: absence is
   the default, and TLS 1.3's own schedule needs no identifier of its
   own.

   Each KDF defined here is a profile of the same deck function.  This
   extendable-output function absorbs the schedule's inputs as length-
   framed strings and squeezes each derived value from the accumulated
   sequence.  It is defined once for both profiles in Section 7, and
   each selects a different permutation for it: TLS13_TURBOSHAKE256
   (Section 8) uses the 12-round TurboSHAKE256 [RFC9861], and
   TLS13_SHAKE256 (Section 9) uses the 24-round SHAKE256 [FIPS202].
   Finished and PSK binder values use one MAC (Section 5.2).  The
   Encrypted Client Hello acceptance value is produced by the deck's
   output operation, Derive (Section 5.7).

1.1.  Design Goals

   A KDF turns the whole derivation surface of a connection into one
   named, testable object.  Every value comes from one permutation,
   every derivation is injectively framed (Section 7.1), and Appendix D
   gives byte-exact values for both profiles.  Neither KDF uses SHA-2,
   HMAC, or HKDF in any role, and the correspondence with TLS 1.3 can be
   audited shape by shape (Section 7.3).

   The alternative is to keep TLS 1.3's HKDF schedule and give it a
   SHA-3 hash.  That inherits TLS 1.3's analysis directly, and
   Appendix E records a variant close to it.

   The deck costs fewer permutation calls than that alternative.  HKDF
   is built on HMAC, and every HMAC call nests two hash calls, overhead
   that exists only to key a hash not built for keying.  A keyed sponge
   needs no such wrapper: it produces each Derive output in one squeeze,
   with no separate extract step between stages.

   Over the representative handshake of Appendix A, the deck costs 29
   Keccak permutation calls against 120 for a hash-only HKDF-SHA3-256
   over the same permutation (Appendix A.2).  HMAC accounts for four
   permutation calls in every HKDF operation, two for each of its nested
   hashes, where a Derive here costs one or two (Appendix B).

1.2.  Scope

   This document does not define a new version of TLS, and defines no
   cipher suites.  It adds one extension.  The state machine, record
   layer, all other wire structures, cipher suites, AEAD algorithms, and
   per-record nonce construction remain those of TLS 1.3.

   A KDF governs only the key schedule and the transcript hash
   (Section 6.1).  Negotiating one does not by itself make a connection
   free of SHA-2: certificate-based authentication is negotiated
   separately and commonly relies on SHA-2.  A deployment that requires
   a fully SHA-2-free connection must additionally restrict itself to
   SHA-2-free signature schemes and certificate chains, or use PSK-only
   authentication (Section 15).  Note also that the cipher suite
   continues to name a hash, which under a KDF of this document governs
   nothing in the key schedule (Section 6.1).

1.3.  Deck Functions

   A key schedule is a derivation tree.  A deck function (Section 7.1)
   expresses that tree directly: absorb a stage's inputs into a running
   accumulator, derive each leaf from a clone, and ratchet the
   accumulator into the next stage.  One XOF does the work HKDF splits
   between Extract, at the stage boundaries, and Expand-Label, at the
   leaves.

   The construction takes no key: a secret is an ordinary framed input,
   and each derivation's bound is the XOF's own, not a keyed-primitive
   assumption, given the premises in Section 15.6.  The operations named
   here, Init, Absorb, Derive, and Ratchet, are defined normatively in
   Section 7.

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   This document uses the following terms.

   KDF:  The key-derivation function of a connection, named by a TLS KDF
      Identifier and negotiated in the schedule_profile extension
      (Section 6).  It defines every key-schedule computation of the
      connection (Section 3) and determines the key schedule: a
      TLS13_TURBOSHAKE256 or TLS13_SHAKE256 identifier implies this
      document's deck schedule (Section 7), and absence of the extension
      implies TLS 1.3's HKDF schedule over the cipher suite's hash.

   selected_cipher_suite:  The cipher suite selected in the ServerHello
      message, as a 16-bit integer.  uint16(selected_cipher_suite)
      yields its two-octet TLS 1.3 encoding.

   associated cipher suite:  The cipher suite associated with a PSK
      (Section 4).

   trunk (stage trunk):  The running deck accumulator for a schedule
      stage (E, H, or T), which absorbs the stage's inputs, is cloned
      for each of the stage's leaf outputs, and is ratcheted at the
      stage boundary to an internal residue that seeds the next stage's
      trunk.

   shared_secret:  The asymmetric shared secret, computed as in
      Section 7.4 of [RFC9846].

   Nk, Nn:  The AEAD key and nonce lengths of the selected cipher suite,
      in octets.

   FLen:  The length of Finished and PSK binder verify_data: 64 octets
      in both profiles of this document.

   uint16(n):  The two-octet big-endian encoding of n, as in the TLS
      presentation language.

   ||:  Octet-string concatenation.

   x[a..b]:  Octets a through b-1 of the octet string x, indexed from
      zero.

   frame(x):  uint16(len(x)) || x, where len(x) is the octet length of
      x.

      Strings are length-prefixed only: they are not null-terminated or
      otherwise padded after x.  Both profiles of this document build
      every derivation input from framed items, so inputs are
      injectively encoded.

      A uint16 encodes 65535, so frame(x) carries any x of 0xFFFF octets
      or fewer, and longer inputs do not occur: variable-length public
      values are reduced by the transcript hash or explicitly bounded
      before framing, and the one variable-length secret input, an
      external PSK, is bounded by Section 10.

   An empty value contributes frame("") wherever it is framed, encoding
   as the two octets 0x0000 with no payload octets.  An absent input
   omits its framed items entirely.  Omitting an input is not the same
   as framing an empty value.

2.1.  Transcript Hash

   The transcript hash is an unkeyed 64-octet hash defined by the
   negotiated KDF (Section 8, Section 9).  TranscriptHash is computed
   over the handshake transcript as in Section 4.1 of [RFC9846]: message
   type and length fields are included, and record-layer framing is
   excluded.  TranscriptHash accepts any octet string.  The TLS 1.3
   rules define only how the handshake transcript is serialized before
   hashing, and the same function is applied to non-transcript inputs
   such as exporter contexts and imported PSK identities.  For a
   HelloRetryRequest, the synthetic-message construction in Section 4.1
   of [RFC9846] is retained, substituting TranscriptHash for Hash.

   In both profiles of this document, TranscriptHash takes no cipher
   suite input, so a client can compute its checkpoints before the
   ServerHello.  The selected suite enters the transcript at the
   ServerHello, separating later outputs as in TLS 1.3.  The
   schedule_profile extension enters the transcript at the ClientHello,
   so TH_CH0, TH_CH, and TH_SH bind the offered KDFs.

   This document uses the following checkpoint values:

   TH_CH0:  TranscriptHash of the partial ClientHello transcript in
      Section 4.3.11.2 of [RFC9846]: the handshake messages through the
      ClientHello, with the ClientHello truncated after the
      PreSharedKeyExtension.identities field and the binders list
      excluded.  After a HelloRetryRequest, this partial transcript
      includes the first ClientHello and the HelloRetryRequest via the
      synthetic-message construction of Section 2.1, exactly as in TLS
      1.3.

   TH_CH:  TranscriptHash(ClientHello).

   TH_SH:  TranscriptHash(ClientHello up to and including ServerHello).

   TH_SF:  TranscriptHash(ClientHello up to and including the server
      Finished message).

   TH_CF:  TranscriptHash(ClientHello up to and including the client
      Finished message).

   For a Finished MAC computed by either peer, the covered transcript is
   taken up to but not including the Finished message being computed,
   consistent with Section 4.5.3 of [RFC9846].

3.  Key-Derivation Functions

   A KDF is a set of algorithms and encodings negotiated in the
   schedule_profile extension (Section 6), independently of the cipher
   suite.  A KDF specifies:

   *  the XOF over which its deck schedule and MAC are instantiated
      (Section 7);

   *  SecretLen, the length of stage and traffic secrets;

   *  FLen, the length of Finished and binder verify_data;

   *  TranscriptHash(messages), the unkeyed transcript hash of
      Section 2.1;

   *  the derivation of initial and stage secrets from PSK and key-
      exchange inputs (an extract operation, a stage accumulator, or an
      equivalent construction);

   *  the derivation of every handshake, application, exporter, and
      resumption secret;

   *  the Finished MAC and PSK binder computations;

   *  record key and IV derivation;

   *  traffic-secret update;

   *  exporter derivation;

   *  resumption PSK derivation;

   *  the Encrypted Client Hello acceptance computations; and

   *  the domain-separation and input-framing rules its derivations use.

   The suite continues to select the AEAD, as in Section 4.2 of
   [RFC9846].  Future specifications may define additional KDFs by
   registering a TLS KDF Identifier (Section 14) whose definition covers
   every computation listed above.

   Every derivation of a KDF MUST bind at least the following into the
   input of the underlying primitive: a protocol identifier (the KDFs of
   this document frame schedule_label, Section 7), the derivation label,
   the output length (a KDF MAY instead fix the length of an internal
   stage secret as a constant, provided the operation that produces it
   is domain-separated from every variable-length operation), the
   transcript checkpoint or other public context where applicable, and
   the secret input or the stage that carries it.  All variable-length
   items MUST be length-framed.  No two distinct derivation paths will
   produce identical encoded inputs to the underlying primitive unless
   they intentionally derive the same value.

   Both profiles of this document bind the output length as uint16, so
   no output longer than 65535 octets is derivable.  The one derivation
   whose length is caller-chosen is the exporter: an implementation MUST
   reject a TLS-Exporter request for more than 65535 octets rather than
   reduce the requested length modulo 65536, which would let two
   different requested lengths bind the same encoded value.  Every other
   output length in this document is a profile constant or Nk + Nn, all
   far below the bound, so the exporter is the only derivation where
   this rejection can occur.

4.  KDF Selection and PSK Compatibility

   The negotiated KDF governs the whole key schedule of a connection,
   the role SHA-256 or SHA-384 plays in Section 7.1 of [RFC9846].  Its
   XOF runs every derivation of the schedule (Section 7).

   A PSK binder is computed before the server selects a cipher suite,
   and verified under the KDF the PSK is bound to.  As in Section 4.3.11
   of [RFC9846], a server MUST verify the binder of any PSK it selects.
   The binder is keyed by a secret derived under that KDF (Section 5.5),
   so a binder computed under one KDF verifies under another only by
   chance.

   A server MUST NOT select a PSK unless the KDF of the connection it
   forms is compatible with the KDF associated with the PSK.  Two KDFs
   are compatible only if they are the same TLS KDF Identifier.  This
   document defines no broader compatibility.  This rule is the analogue
   of RFC 9846, Section 4.3.11, which requires a resumption to share the
   PSK's hash: under this document the KDF is the hash (Section 6.1).  A
   client MUST abort the handshake with an illegal_parameter alert if
   the server selects a PSK whose KDF is incompatible with the selected
   KDF, as that section requires of the hash.

   Otherwise a 1-RTT resumption follows TLS 1.3.  The selected cipher
   suite need not equal the PSK's associated cipher suite.  A resumption
   MAY change the AEAD as long as the KDFs are compatible.  The selected
   suite appears in the ServerHello and therefore in the transcript,
   which separates every handshake and application output as in TLS 1.3
   (Section 15.2).

   After a HelloRetryRequest, an updated binder remains under the PSK's
   KDF.  A client SHOULD omit from its updated ClientHello any PSK whose
   KDF is incompatible with the KDF implied by the HelloRetryRequest,
   and MUST recompute binders as required by Section 4.3.11.2 of
   [RFC9846].

   For 0-RTT, the server MUST require the selected cipher suite to equal
   the PSK's associated cipher suite (Section 11).  This is TLS 1.3's
   own 0-RTT rule.

   A PSK that is offered but not selected leaves no trace in the
   schedule.  If the server does not select the client's PSK, both peers
   compute the connection's schedule as a handshake without a PSK: the
   client discards any PSK-keyed schedule state it built for the binder
   or for early data, along with its outputs, and begins the schedule
   again with the empty PSK, applying the destruction rules of its KDF.

   Implementations MUST associate every PSK and session ticket with its
   KDF to select a compatible PSK and compute its binder.  For an
   imported PSK, this is its target_kdf (Section 10).  Implementations
   MUST also retain the PSK's associated early-data parameters (cipher
   suite, ALPN, and early-data permission).  As in Section 4.3.10 of
   [RFC9846], these are provisioned along with the key for external
   PSKs, including imported PSKs, and negotiated when the PSK was
   established for resumption PSKs and session tickets.  An imported PSK
   without provisioned early-data parameters is not eligible for early
   data.

5.  Keyed Derivations

   Every derivation in this document that is keyed by a retained octet-
   string secret, rather than by a live stage of a profile's schedule,
   is a deck session rooted at that secret (Section 7), specified once
   for both profiles in Section 5.1 since the deck is identical up to
   its permutation.  MAC, which computes the Finished and PSK binder
   tags, is one such derivation (Section 5.2).  Stage schedules
   themselves remain profile-specific (Section 8, Section 9).

5.1.  Deriving from a Retained Secret

   A value keyed by a retained octet-string secret is a Derive
   (Section 7.1) whose deck is seeded with that secret rather than run
   as a live stage trunk.  The seed is the secret itself: Init(secret),
   the same way a ratchet seeds the next stage with its residue.  Derive
   then adds the context under the "ctx_" tag if any, the label, and the
   output length under the "out_" tag:

D     = Init(secret)                # Init frames schedule_label, "seed"
value = Derive(D, label, [context], [L])

   label is one of this document's 3-octet labels (Section 7.2), context
   is an octet string, and L is the output length in octets.  Every item
   is length-framed by the deck (Section 15.8), so distinct derivations
   map to distinct deck inputs.  An empty context is omitted rather than
   framed as an empty value, and omission is its canonical encoding.  It
   differs from an explicitly framed empty value, because after an
   omitted context the next item is the label, not frame("ctx_").  L
   never exceeds 65535 octets (Section 3).  Such a Derive is the
   analogue of TLS 1.3's HKDF-Expand-Label, and Section 7.2 gives the
   TLS 1.3 label that each of its labels replaces.

   The following retained-secret derivations are instances of this
   shape, each fixing the base secret, label, context, and output
   length.  The exporter (Section 5.6) uses two such derivations, with
   the raw exporter label as the first context and the context hash as
   the second.  The ECH acceptance confirmations (Section 5.7) take a
   transcript hash as context, and MAC (Section 5.2) takes the message
   it authenticates.  Every derivation of this shape carries its context
   under the "ctx_" tag, including one whose context is itself a
   transcript hash.

   1.  Record keys (Section 5.3): base secret, a traffic secret; label,
       "key"; no context; length, Nk + Nn.

   2.  Next traffic secret (Section 5.4): base secret, the current
       traffic secret; label, "upd"; no context; length, SecretLen.

   3.  resumption_psk: base secret, resumption_secret; label, "rsp";
       context, ticket_nonce; length, SecretLen.

   4.  ipsk (Section 5.8): base secret, epsk; label, "ipk"; context,
       TranscriptHash(ImportedIdentity), the transcript-hash reduction
       defined in Section 5.8; length, SecretLen.

5.2.  MAC

   MAC(key, message, L) computes every tag in this document: the PSK
   binder and both Finished values.  It is a Derive over a deck seeded
   with the key (Section 5.1), with the label "mac" and the message as
   its context:

   MAC(key, message, L) = Derive(Init(key), "mac", message, L)

   Every MAC of this document takes a 64-octet key and a 64-octet
   transcript hash as its message, so its input to DF (Section 7.1) is
   these 167 octets, with the key and the message each starting on an
   8-octet boundary (Section 7.2):

   offset
        0  0x0006 || "tls13 "    frame(schedule_label), from Init
        8  0x0004 || "seed"      frame("seed")
       14  0x0040 || key         frame(key), at offset 16
       80  0x0004 || "ctx_"      frame("ctx_")
       86  0x0040 || message     frame(message), at offset 88
      152  0x0003 || "mac"       frame("mac"), the label
      157  0x0004 || "out_"      frame("out_")
      163  0x0002 || uint16(L)   frame(uint16(L))

   No other derivation of this document uses the label "mac", so a MAC
   input is never the input of another derivation (Section 15.8).  The
   output length is bound by the "out_" item as in every Derive, so tags
   of different lengths are computed over different inputs.  MAC is the
   analogue of TLS 1.3's HMAC-based Finished and binder MACs, and like
   them it is keyed by a dedicated key that keys nothing else
   (Section 5.5).  Both Finished values are computed the same way, each
   over a different key and a different message.  L never exceeds 65535
   octets (Section 3).

   MAC uses the profile's DF and nothing else, so it needs no primitive
   beyond the SHAKE256 [FIPS202] or TurboSHAKE256 [RFC9861] that
   computes every other derivation and the transcript hash.

5.3.  Record Keys

   Record keys are the "key" derivation of Section 5.1: a traffic secret
   derived in one call to key_block, so a retained traffic secret
   suffices to re-derive its keys, as in TLS 1.3.  For early-data keys,
   derived before the ServerHello, Nk and Nn are those of the offered
   PSK's associated cipher suite.  For every other traffic secret they
   are those of selected_cipher_suite.

   key_block is that derivation: the traffic secret as the seed, the
   label "key", no context, and output length Nk + Nn.

   # no context, so the third argument is the output length
   key_block = Derive(Init(traffic_secret), "key", Nk + Nn)
   write_key = key_block[0..Nk]
   write_iv  = key_block[Nk..Nk+Nn]

   The split is unambiguous: Nk and Nn are fixed by the suite, and their
   sum is bound into the derivation as the output length.  The traffic
   secret is already specific to one direction and one stage, so no
   direction or epoch input is needed.  The per-record nonce
   construction, record format, and AEAD additional data are unchanged
   from TLS 1.3.

5.4.  Key Update

   A key update derives the next traffic-secret generation,
   app_traffic_secret_{N+1}, from the current one by the "upd"
   derivation of Section 5.1, with record keys re-derived from the new
   secret as above.  An implementation MUST NOT derive generation N+1
   from anything other than generation N, in particular not from a
   retained stage accumulator or a counter: that rule determines the
   derived value and so is an interoperability requirement.  Each
   generation is also an erasure boundary, and the previous secret, its
   keys, and any schedule state derived from them are destroyed once the
   new generation is installed (Section 15.7).

5.5.  Finished and PSK Binder MACs

   Finished and PSK binder verify_data are computed under a dedicated
   MAC key, derived from a stage or traffic secret (Section 5.1), rather
   than by MACing that secret directly.  This matches Section 4.5.3 of
   [RFC9846]: finished_key and binder_key take the roles of TLS 1.3's
   identically named intermediates, and MAC takes the role of TLS 1.3's
   HMAC.

   finished_key = Derive(Init(base_key), "fin")
   verify_data  = MAC(finished_key, th, FLen)

   For a Finished message, base_key is the base key that message takes
   in the authentication-input table of Section 4.5 of [RFC9846]: the
   sender's handshake traffic secret for a Finished sent during the
   handshake, and the sender's current application traffic secret for a
   post-handshake authentication Finished.  The label is "fin", and th
   covers the transcript up to but not including the Finished message
   being computed.  For a PSK binder, the dedicated key is derived in
   two steps, as TLS 1.3 derives binder_key in Section 7.1 and then
   finished_key from it in Section 4.3.11.2, via Section 4.5.3:

   binder_key   = Derive(E, binder_label)
   finished_key = Derive(Init(binder_key), "fin")
   verify_data  = MAC(finished_key, TH_CH0, FLen)

   E is the live early trunk of the schedule keyed by that PSK, before
   its ratchet (Section 7.4).  binder_key is a Derive directly on E, a
   third early leaf alongside c_e_traffic and early_exporter_secret, so
   the early trunk is the analogue of TLS 1.3's Early Secret from which
   Section 7.1 of [RFC9846] derives binder_key.  binder_label is "ebk"
   for a non-imported external PSK, replacing "ext binder", "ibk" for an
   imported PSK, replacing "imp binder" from Section 5.2 of [RFC9258],
   and "rbk" for a resumption PSK, replacing "res binder".

   finished_key is derived under "fin" for both a Finished and a binder,
   and the two are already separated one step up by their base secret, a
   traffic secret against binder_key.  Both finished_key and binder_key
   are 64 octets, the length of every stage and traffic secret in both
   profiles (SecretLen, Section 8, Section 9), matching TLS 1.3's use of
   Hash.length for the same intermediates.  Binder verification follows
   Section 4.

   Appendix A counts every finished_key and binder_key derivation of a
   representative full handshake against the corresponding TLS 1.3 HKDF-
   Expand-Label calls.

   Each finished_key is a dedicated MAC key, and a Finished MAC key
   shares its base key, the sender's traffic secret, with that sender's
   record keys (Section 5.3).  Their separation from the record keys
   follows from domain separation (Section 15.8).  Sharing the base
   secret reproduces TLS 1.3's structure and its exposure exactly
   (Section 15.6); this document establishes no separate joint-security
   argument for that sharing (Section 15.6.4).

   Binders are computed before the ServerHello.  This is possible in
   both profiles because the early trunk binds no cipher suite: the
   client clones the early trunk to obtain binder_key at ClientHello
   time, in either profile (Section 7).

5.6.  Exporters

   Exporters use two retained-secret derivations, following the shape of
   Section 7.5 of [RFC9846]:

   TLS-Exporter(label, context, length):
       exporter_label_secret = Derive(Init(exporter_secret), "exl",
                                      label, SecretLen)
       return Derive(Init(exporter_label_secret), "exp",
                     TranscriptHash(context), length)

   The early exporter is the same construction keyed by
   early_exporter_secret.  The raw label is the first Derive's context
   and is framed under "ctx_" (Section 5.1).  An implementation MUST
   reject a TLS-Exporter request whose label exceeds the 65535-octet
   frame limit, rather than reduce its length modulo 65536.

   The intermediate lets an implementation that knows all its exporter
   labels derive their label secrets and then erase exporter_secret, as
   Appendix F.1.4 of [RFC9846] recommends.

   Framing the raw label separates inputs to the first Derive without
   relying on TranscriptHash collision resistance for that separation.
   The second Derive takes the context hash because the context has
   unbounded length.  An implementation MUST reject a TLS-Exporter
   request for more than 65535 octets of output (Section 3).

5.7.  ECH Acceptance Confirmations

   For the KDFs of this document, the ECH acceptance signals of
   [RFC9849] are:

   D = Init(ClientHelloInner.random)

   accept_confirmation =
       Derive(D, "eca",
              TranscriptHash(ech_conf_messages), 8)

   hrr_accept_confirmation =
       Derive(D, "hca",
              TranscriptHash(hrr_ech_conf_messages), 8)

   replacing the HKDF-Extract and HKDF-Expand-Label computations of
   [RFC9849] and its labels "ech accept confirmation" and "hrr ech
   accept confirmation", with ech_conf_messages and
   hrr_ech_conf_messages the handshake message ranges that document
   identifies for each confirmation, per Section 4.1 of [RFC9846].
   TranscriptHash(ech_conf_messages) is RFC 9849's transcript_ech_conf,
   the same single transcript-hash operation, applied once.

   Keying the confirmation on ClientHelloInner.random alone matches
   [RFC9849], whose confirmation key is HKDF-Extract(0,
   ClientHelloInner.random), with no handshake secret mixed in.  This
   document seeds a deck with that same value and takes one Derive, in
   place of RFC 9849's extract-then-expand, so the acceptance signal
   keeps its RFC 9849 properties.  Only a server that holds
   ClientHelloInner.random can compute the confirmation.  A network
   attacker without that value is left to guess the 8 octets, succeeding
   with probability 2^-64 if the Derive output is pseudorandom.  Because
   each confirmation's transcript covers the message that carries it,
   the ServerHello or the HelloRetryRequest, it binds its handshake and
   does not transplant to another.

5.8.  PSK Import Derivation

   An external PSK is imported per target KDF (Section 10).  For every
   KDF of this document, ipsk is the "ipk" derivation of Section 5.1,
   keyed by epsk with TranscriptHash(ImportedIdentity) as context, with
   target_kdf as the KDF.  This follows the shape of the RFC 9258
   derivation, with the entire serialized ImportedIdentity reduced by
   the transcript hash as the context.  ipsk is an explicit octet string
   by design: it crosses a system boundary into the PSK store.  epsk is
   absorbed as the secret of a deck derivation (Section 5.1) in both
   profiles, so a low-entropy or attacker-influenced epsk never keys
   either profile's underlying permutation directly.

6.  Negotiating a KDF

   This document defines no cipher suites.  A connection uses the cipher
   suites of TLS 1.3, and negotiates its KDF separately, in a new
   extension.

   Coupling the two would make the offered set the product of the AEAD
   choices and the schedule choices, and would oblige a client that
   wants one schedule with two AEADs to carry a code point for each
   combination.  The schedule and the AEAD are independent choices, and
   this document negotiates them independently.

   The value negotiated is a TLS KDF Identifier, the registry [RFC9258]
   already created for naming a key schedule independently of a cipher
   suite.  A KDF of this document registers there (Section 14).

   struct {
       uint16 profiles<2..2^16-2>;   /* TLS KDF Identifiers */
   } ScheduleProfileList;

   The extension_data of a schedule_profile extension (Section 14) is a
   ScheduleProfileList in a ClientHello, in preference order, and a
   single uint16 in a ServerHello or a HelloRetryRequest.

   Absence is the default, and the default is TLS 1.3: a connection
   whose ClientHello omits the extension, or whose server does not echo
   it, runs the key schedule in Section 7.1 of [RFC9846], HKDF over the
   negotiated cipher suite's hash.  That is HKDF_SHA256 or HKDF_SHA384
   as the suite's hash determines, so TLS 1.3's own schedule needs no
   value of its own here and an endpoint of this document interoperates
   with TLS 1.3 unchanged.

   A client that requires an alternative schedule MUST abort with a
   handshake_failure alert if the ServerHello omits the extension
   (Section 15.2).  The offered list does not signal whether the client
   requires an alternative schedule or permits fallback.  Because
   absence is the sole signal for the TLS 1.3 schedule, a
   ScheduleProfileList MUST NOT include HKDF_SHA256 or HKDF_SHA384, the
   other values of the RFC 9258 registry.  A server that receives either
   MUST treat it as if that KDF were not offered, and MUST NOT select
   it.

   The KDFs of this document are TLS13_TURBOSHAKE256 (Section 8) and
   TLS13_SHAKE256 (Section 9).

   A server MUST NOT select a KDF the client did not offer.  A client
   MUST abort the handshake with an illegal_parameter alert if the
   ServerHello or HelloRetryRequest selects a KDF it did not offer, as
   Section 4.2.3 of [RFC9846] requires for the cipher suite.  A server
   that selects a KDF of this document MUST send the extension in its
   ServerHello, so the selection is covered by the transcript
   (Section 15.2).

   A server that sends a HelloRetryRequest and selects a KDF of this
   document MUST carry the selected KDF as a schedule_profile extension
   in the HelloRetryRequest.  That selection pins the KDF for the rest
   of the handshake and is the KDF implied by the HelloRetryRequest
   (Section 4).  The client computes its second ClientHello and every
   later checkpoint under that KDF, and the HelloRetryRequest is covered
   by the transcript.  A HelloRetryRequest without the extension selects
   the TLS 1.3 schedule for the rest of the handshake, and the server
   MUST NOT then send the extension in its ServerHello.  A client MUST
   abort the handshake with an illegal_parameter alert if the
   ServerHello's schedule_profile, present or absent, differs from the
   HelloRetryRequest's, as Section 4.2.4 of [RFC9846] requires for the
   cipher suite.

6.1.  What the KDF Governs

   A KDF defines every key-schedule computation of the connection,
   including the transcript hash (Section 3).  When a KDF of this
   document is negotiated, the hash named by the cipher suite governs
   nothing in the key schedule: the transcript hash is the KDF's, and
   the derivations and MACs are the KDF's.  The transcript hash a
   CertificateVerify signs (Section 4.5.2 of [RFC9846]) is also the
   KDF's TranscriptHash.

   The cipher suite's name still carries that hash.  A connection on
   TLS_AES_128_GCM_SHA256 with TLS13_TURBOSHAKE256 selected takes AES-
   128-GCM, its Nk and Nn, and its per-record nonce construction from
   the suite, and takes SHA-256 from nowhere: no part of the key
   schedule uses it.  A connection that negotiates no KDF is unaffected:
   the suite's hash governs its schedule exactly as TLS 1.3 specifies.

7.  The Deck Schedule

   Both KDFs of this document express the key schedule as a deck
   function (Section 1.3).

   The schedule's normative interface is defined here, in terms of the
   profile's XOF and nothing else: Init and Absorb build a framed input
   sequence, Derive reads one to produce a keyed output, and Ratchet
   crosses a stage boundary.  Each Derive is one XOF call over its input
   sequence.  Its bound is the XOF's own, given the premises in
   Section 15.6, not a contract inherited from an abstraction.
   Section 8 and Section 9 each give a short instantiation naming the
   profile's XOF, permutation, and domain-separation constants.

   This document uses the following terms.

   schedule_label:  The fixed 6-octet ASCII string "tls13 " (with a
      trailing space), framed at Init (Section 7.1) into every
      derivation of both profiles.  It marks the TLS 1.3 deck schedule
      and is identical for both profiles, which are separated by their
      XOF, not by this label.  It is byte-identical to the "tls13 "
      label prefix in Section 7.1 of [RFC9846].  Its byte-level
      separation from other uses of the same XOF, including the
      transcript hash, is covered in Section 15.8.

   deck function:  An extendable-output function evaluated over a
      sequence of framed input strings, with the output length bound
      into the sequence before any output is produced (Section 7.1).
      The construction beneath it is an XOF and takes no key parameter,
      its secrets being ordinary framed inputs.  Related keyed-sponge
      results are discussed in Section 15.9.

   stage:  One of the three phases of the schedule: early (keyed by the
      PSK), handshake (adds the key-exchange secrets), and application.
      Stages are separated by ratchets (Section 7.1).  A key update is a
      derivation of the retained traffic secret (Section 5.4), not a
      ratchet.

   ratchet:  Crossing a stage boundary with the Ratchet operation of
      Section 7.1: the residue is Derive(D, "drv"), and the next deck is
      Init'd, framing schedule_label, then seeded with that residue,
      after which the completed deck is destroyed (Section 15.7).

   The presentation is stateful, but the construction is not.  Each
   Derive equals one invocation of a profile's deck function over its
   framed input sequence.  The three stages of Section 7.4 are protocol
   phases separated by ratchets, not KDF steps: shared trunks absorb
   each input once, the two ratchet residues connect the stages, and the
   one-way truncations fall at the stage boundaries where TLS must erase
   prior state.

7.1.  The Deck Schedule Interface

   A deck is a running sequence of framed inputs.  The profile's DF(S,
   L) is the XOF over that sequence (Section 8.1, Section 9.1).  It
   returns L octets, and L is at most 65535.  The schedule runs one deck
   per stage, driven by four operations.

7.1.1.  Operations

 Init([seed])         D = frame(schedule_label)
                          [ || frame("seed") || frame(seed) ]

 Absorb(D, tag, v)    D = D || frame(tag) || frame(v)

 Derive(D, label,     out = DF(D [ || frame(ctag) || frame(context) ]
        [context], [L])         || frame(label)
                                || frame("out_") || frame(uint16(L)), L)
                      # D is cloned, not consumed
                      # ctag names context, as tag names v in Absorb
                      # omitted L is SecretLen

 Ratchet(D)           residue = Derive(D, "drv")
                      return Init(residue)
                      # analogue of Derive-Secret(., "derived", "")
                      # the next deck is Init, seeded with the residue

   Init starts a deck by framing schedule_label.  Every deck is Init'd,
   so every keyed sequence opens with frame(schedule_label), TLS 1.3's
   label prefix (Section 15.8).  A ratchet residue or a retained secret
   is passed to Init as the seed and framed under the tag "seed"
   (Section 7.4, Section 5.1).  Absorb feeds one tagged input into the
   running deck.  That is the same role HKDF-Extract's mixing step plays
   in TLS 1.3.

   Derive is the keyed-output operation.  It clones the running deck,
   absorbs that leaf's context, then adds the leaf label.  The deck
   being derived from fixes ctag: a live stage trunk takes "th__", whose
   context is a transcript checkpoint, and a deck seeded from a retained
   secret takes "ctx_", whose context is that derivation's expansion
   context.  A Derive with no context frames neither.  The context
   precedes the label here, the reverse of TLS 1.3's HkdfLabel order.
   The framing is injective either way, and placing the context first
   lets sibling leaves that share it branch after one absorption.

   The clone leaves the deck unchanged, so one deck yields all of a
   stage's leaves.  Derive fills exactly HKDF-Expand-Label's role.  At a
   stage leaf it stands in for TLS 1.3's Derive-Secret(secret, label,
   Messages), with the deck in place of the secret.  A value keyed by a
   retained secret is a Derive over a deck seeded with that secret
   (Section 5.1).  A Derive that omits L, including every leaf of the
   key schedule (Section 7.4) and the Ratchet residue, outputs SecretLen
   octets.  A Derive that fixes its own length passes L explicitly
   (record keys, exporters, the ECH confirmation, MAC).

   Ratchet crosses a stage boundary.  Its residue is a Derive under the
   label "drv", which is this schedule's analogue of TLS 1.3's Derive-
   Secret(., "derived", "") between stages.  The next deck is Init'd
   like any other, framing schedule_label, then seeded with that
   residue, so "drv" names the residue, not the new deck.  The residue
   is internal and never leaves the schedule.  Any stage input, such as
   the asymmetric shared secret, is a later Absorb into the new deck,
   not part of the ratchet.

   The old deck is retired: nothing absorbs into it or derives from it
   afterward.  Because the residue is a squeeze, recovering the retired
   state from it takes a query on the secret-bearing input in the
   random-oracle game, provided the old deck was erased (Section 15.7).
   This is not the in-place Ratchet() of Cyclist or STROBE ([XOODYAK],
   [STROBE]), which returns nothing.

   A Derive is one DF call over its framed path, and a ratchet residue
   is one such Derive.  It is therefore byte-exact and testable alone.

7.2.  Labels and Alignment

   schedule_label is 6 octets and every tag is 4 octets, so
   frame(schedule_label) fills 8 octets and every framed tag, together
   with the two-octet length of the value it names, fills 8 more.  A
   value framed under a tag therefore starts on an 8-octet boundary
   whenever every value before it in the deck input is a multiple of 8
   octets long, which lets an implementation that absorbs 64-bit lanes
   take key material without realigning it.  With the 64-octet secrets
   and transcript hashes of this document, that holds for the PSK and
   every seed, at offset 16, for the first asymmetric shared secret
   component, at offset 88, for every transcript checkpoint and MAC
   message that follows only such values, and for the context of the ECH
   confirmations, at offset 56.

   It does not hold after a value whose length is not a multiple of 8.
   A P-521 shared secret is 66 octets, so the transcript checkpoint
   after it starts at offset 162, and an external PSK has arbitrary
   length, so the context of its import derivation may be unaligned.  In
   the exporter (Section 5.6), the raw label in the first Derive and the
   context hash in the second each start at offset 88: 8 octets for
   frame(schedule_label), 72 for the tagged seed, and 8 for
   frame("ctx_") and the context's length.

   Every derivation label is 3 octets.  A derivation label is the last
   item before the output length, so its length does not bear on
   alignment, and a short label keeps the tail of a Derive at 15 octets.
   Labels and tags are absorbed as they are.  Apart from handshake
   transcript hashes, the only inputs reduced by TranscriptHash before
   framing are the exporter context and the ImportedIdentity, whose
   lengths are not bounded by this document (Section 5.6, Section 5.8).

   Tags shorter than four letters are padded with underscores.  The tags
   are:

7.3.  Derivation Shapes

   Every TLS 1.3 derivation replaced by this document is an instance of
   one of six shapes.

   1.  Root absorb: the Early Secret extract, as Init + Absorb.

   2.  Accumulate: the Handshake Secret extract IKM, per component, as
       Absorb.

   3.  Ratchet: Derive-Secret(., "derived", "") at a boundary, as
       Ratchet.

   4.  Deck derive: traffic and exporter secrets, PSK binder keys, as
       Derive.

   5.  Secret derive: record keys, exporter label secrets and outputs,
       key update, resumption, PSK import ([RFC9258]), as Derive.

   6.  Keyed check: Finished and PSK binders, as MAC.

   Shapes 1 through 3 act on the trunk of a stage.  Shapes 4 and 5 are
   the same operation, Derive, over a live trunk or over a seeded deck
   rooted at a retained secret (Section 5.1).  Shape 6 is shape 5 under
   the label "mac", with the message as context (Section 5.2).  Record
   keys are derived from their traffic secret by a separate call, as in
   TLS 1.3, so a retained traffic secret suffices to re-derive its keys.
   Deriving them within the call that produces the traffic secret would
   save a few invocations but break that re-derivability, so the
   schedule keeps the separate call.

7.4.  Key Schedule

   The schedule has three stages separated by two ratchets.  A key-
   update generation is a derivation of the retained traffic secret
   (Section 5.4), not a further ratchet.  Stage trunks and stage secrets
   bind no cipher suite value, matching the TLS 1.3 extracts they
   replace; no leaf derivation binds one directly either.  A client
   offering several cipher suites under one KDF computes one schedule.
   Only record-key derivations depend directly on the suite, through
   their Nk + Nn output length (Section 5.3).  Every derivation frames
   schedule_label at Init (Section 7.1).  The negotiated KDF is bound by
   the XOF, not by this label.  This listing is identical for both
   profiles.  Only each profile's DF instantiation differs (Section 8,
   Section 9).

   E = Init()
   Absorb(E, "psk_", PSK)             # "" when no PSK is selected

   # early-stage leaves, each a clone of the early deck E
   c_e_traffic           = Derive(E, "cet", TH_CH)      # 0-RTT
   early_exporter_secret = Derive(E, "ees", TH_CH)      # 0-RTT
   binder_key            = Derive(E, binder_label)     # no context

   H = Ratchet(E)                     # residue = Derive(E, "drv")
                                      # then H = Init(residue)
   Absorb(H, "shs_", shared_secret)   # once per key-exchange component

   c_hs_traffic = Derive(H, "cht", TH_SH)
   s_hs_traffic = Derive(H, "sht", TH_SH)

   T = Ratchet(H)                     # residue = Derive(H, "drv")
                                      # then T = Init(residue)

   c_ap_traffic      = Derive(T, "cat", TH_SF)
   s_ap_traffic      = Derive(T, "sat", TH_SF)
   exporter_secret   = Derive(T, "exs", TH_SF)
   resumption_secret = Derive(T, "rss", TH_CF)
   # T destroyed

   When the negotiated group is a hybrid or other multi-component key
   exchange, shared_secret denotes the ordered list of component shared
   secrets whose concatenation the group specification defines as its
   shared secret (for example, [RFC9954]).  Both peers MUST use exactly
   those components in that concatenation order, absorbing each with its
   own Absorb(H, "shs_", component), without first concatenating them.

7.4.1.  Absent and Empty Inputs

   A handshake without a PSK still executes Absorb(E, "psk_", "").  That
   call contributes the following bytes:

   frame("psk_") = 0x0004 || "psk_"
   frame("")     = 0x0000

   This is unambiguous because a PSK of this document is never zero-
   length: an imported or resumption PSK is 64 octets (Section 10), and
   an endpoint MUST NOT use an empty raw external PSK.  Without a PSK,
   the early stage carries no leaves and its deck holds only known
   constants, as TLS 1.3's Early Secret is the extract of two known
   constants.  The stage exists for uniformity across handshake modes,
   and the schedule's security does not rest on its secrecy when no PSK
   is present.  A PSK-only handshake omits Absorb(H, "shs_", ...)
   entirely: the tag "shs_" does not appear in the sequence.

7.4.2.  Stage Secrets

   The three stage decks E, H, and T are this schedule's analogue of TLS
   1.3's Early, Handshake, and Main Secret.  They are states, not
   values.  A leaf clones the running deck rather than reading an
   extracted octet string, so no named early or main secret is
   materialized.

   Each stage boundary is a Ratchet (Section 7.1) whose residue is
   Derive(D, "drv"), and whose next deck is Init'd, framing
   schedule_label, and seeded with that residue.  That residue is the
   analogue of TLS 1.3's unnamed "derived" salt.  It never leaves the
   schedule.  It seeds the next deck once and is then discarded
   (Section 15.7).

   The values that do leave, the traffic and exporter secrets, are
   separated by their framed paths (Section 15.8): sibling leaves within
   a stage differ by label, and every leaf also binds its transcript
   checkpoint.  Early data is separated in addition by the 0-RTT
   equality check (Section 4).  Every stage binds its transcript at the
   leaves, so the decks themselves bind none.  The derivation graph maps
   onto the TLS 1.3 graph (Section 15.6.3).

8.  The TLS13_TURBOSHAKE256 Profile

   The TLS13_TURBOSHAKE256 profile instantiates the deck schedule of
   Section 7 with TurboSHAKE256 [RFC9861], built on the 12-round Keccak-
   p[1600,12] permutation of [FIPS202].

   The profile parameters are:

   SecretLen:  64 octets, the length of every stage and traffic secret.

   FLen:  64 octets.

8.1.  Instantiation

   The deck function is:

   DF(S, L) = TurboSHAKE256(seq(S), 0x1F, L)

   where seq(S) is the concatenation of every framed item of S in order.
   TurboSHAKE256's output length is in octets per [RFC9861], so L is
   passed unchanged, unlike the SHAKE256 profile, whose bit-oriented
   length needs an 8 * L conversion (Section 9.1).

   The transcript hash of Section 2.1 is instantiated with the same
   function: TranscriptHash(x) = TurboSHAKE256("tls13 hash" || x, 0x1F,
   64).  The domain-separation byte is fixed to 0x1F, the RFC 9861
   default, for every use of TurboSHAKE256 in this profile, so an API
   without the D parameter implements the profile unchanged.

   TurboSHAKE256 uses the Keccak-p[1600,12] permutation as a sponge:
   input is absorbed into a 1600-bit state in rate-sized blocks of 136
   octets, with the permutation applied after each block, and output is
   read from the same state.  The capacity is the 512-bit portion of the
   state that input and output never touch.  It is what the erasure
   argument of Section 15.7 relies on, and the 64-octet secret,
   transcript-hash, and Finished and binder MAC lengths are set to match
   it.

8.1.1.  Required API Surface

   The required API surface is incremental absorption, cloning of an
   unfinalized state, and one-shot squeeze with the output length known
   up front.  Cloning before any output is incremental input to two
   separate invocations, which Section 2.1 of [RFC9861] permits.  No
   absorb-after-squeeze occurs anywhere in this document, so no access
   below the TurboSHAKE interface is required.  The clone discipline is
   the same one TLS stacks already apply to SHA-2 transcript-hash
   checkpoints.

9.  The TLS13_SHAKE256 Profile

   The TLS13_SHAKE256 profile instantiates the deck schedule of
   Section 7 with plain SHAKE256 [FIPS202], built on the 24-round
   Keccak-f[1600] permutation, in place of TurboSHAKE256's Keccak-
   p[1600,12].  This profile mirrors the TLS13_TURBOSHAKE256 profile's
   framing exactly: domain separation comes from the same framed-prefix
   mechanism the TurboSHAKE profile uses, an absorbed
   frame(schedule_label) at Init (Section 7.1), not from cSHAKE's
   function-name and customization-string inputs.  The two profiles'
   decks therefore differ only in the underlying permutation, so
   derivation (Section 5.1) and the MAC construction (Section 5.2) are
   shared by both profiles.

   The profile parameters, SecretLen and FLen, are 64 octets as in
   Section 8.

9.1.  Instantiation

   The deck function is:

   DF(S, L) = SHAKE256(seq(S), 8 * L)

   where seq(S) is the concatenation of every framed item of S in order,
   SHAKE256(X, L) is the function of [FIPS202] with X the main input and
   L the output length in bits, and 8 * L converts this document's
   octet-oriented L to the bit-oriented L argument of SHAKE256.

   SHAKE256 takes no function-name or customization-string input.  This
   profile's domain separation comes from seq(S) beginning with
   frame(schedule_label), as Section 9 describes (Section 7.1).

   The transcript hash of Section 2.1 is instantiated with the same
   function: TranscriptHash(x) = SHAKE256("tls13 hash" || x, 512).

   SHAKE256 uses the Keccak-f[1600] permutation as a sponge with the
   same 136-octet rate and 512-bit capacity as TurboSHAKE256
   (Section 8.1).  The capacity is what the erasure argument of
   Section 15.7 relies on, and the 64-octet secret, transcript-hash, and
   Finished and binder MAC lengths match it in both profiles.

9.1.1.  Required API Surface

   The required API surface is that of Section 8.1: no absorb-after-
   squeeze occurs, so no access below the SHAKE256 interface is
   required.

10.  PSK Importer

   TLS 1.3 permits external PSKs [RFC9846], and [RFC9258] imports an
   external PSK into a target KDF, producing a PSK bound to its target.
   This document updates the importer computation in Section 5.1 of
   [RFC9258] for the KDFs defined here.  It replaces HKDF-Extract and
   HKDF-Expand-Label using the EPSK-associated hash, or its SHA-256
   default, with the target KDF's "ipk" derivation and TranscriptHash
   (Section 5.8).  RFC 9258 uses the target KDF only for output length
   and identity separation; this document also uses it to select the
   importer computation, avoiding a SHA-2 dependency.

   A provisioning importer taught only the new TLS KDF Identifier and
   output length still applies RFC 9258's EPSK-associated-hash rule.  It
   produces a different ipsk for the same ImportedIdentity than the
   importer specified here.  A peer using this document's computation
   discovers the mismatch at binder verification.

   A KDF of this document is a TLS KDF Identifier (Section 14), so an
   external PSK imported for use with one is imported under RFC 9258's
   own ImportedIdentity, with target_kdf naming the KDF.  No variant
   structure is needed, and none is defined.

   The earlier coupling is what made a variant structure seem necessary.
   RFC 9258 binds an imported PSK to a KDF and not to a cipher suite,
   deliberately, so that a PSK cannot be reused across key schedules.  A
   design in which the cipher suite selects the schedule has no KDF to
   name, and has to bind the suite instead.  Negotiating the schedule in
   its own extension removes the problem rather than working around it:
   the thing RFC 9258 wants to bind is once again a value the protocol
   negotiates.

   The import derivation is the generic derivation of Section 5.8, keyed
   by epsk under target_kdf.  An endpoint MUST NOT import an epsk, or
   use a raw external PSK, longer than 0xFFFF octets, so every framed
   value fits a single frame.  A client that imports one external PSK
   for use under more than one KDF MUST produce a separate
   ImportedIdentity, and hence a separate ipsk, per target_kdf, exactly
   as RFC 9258 requires.

   Import is RECOMMENDED.  As in [RFC9258], it is not required.  A raw
   external PSK is associated with its KDF when it is established.  One
   established without a KDF is associated with SHA-256, as
   Section 4.3.11 of [RFC9846] specifies for an external PSK without a
   hash, and so with the TLS 1.3 schedule rather than a KDF of this
   document.  A raw external PSK carries no binding to the KDF it is
   used under, and its length is whatever provisioning chose, so a
   length that is not a multiple of 8 leaves the items after it
   unaligned (Section 7.2) and may cost one further permutation.  An
   imported PSK is SecretLen octets and raises neither question.

   For imports into these KDFs, target-KDF selection also supersedes the
   single-associated-hash restriction in Section 4 of [RFC9258].  The
   separate ImportedIdentity values bind each ipsk to one target KDF,
   preventing reuse of one imported PSK across TLS schedules.  They do
   not isolate the underlying epsk from the different importer KDFs:
   importing the same epsk for both profiles feeds that secret to both
   permutations (Section 15.1).

11.  Zero-RTT and Early Data

   Early data remains PSK-only and remains replayable under the TLS 1.3
   anti-replay model.  This document changes neither.  A client MAY send
   early data using the first offered PSK's associated parameters
   (Section 4) only if they permit early data and the associated cipher
   suite is among those it offers.  A server MUST reject early data
   unless the offered PSK's associated parameters permit early data, the
   selected cipher suite equals the offered PSK's associated cipher
   suite, the selected ALPN equals the PSK's associated ALPN, and all
   TLS 1.3 anti-replay checks pass.  The suite-equality check, not the
   binder, prevents redirecting early data to a different AEAD.

12.  Alerts

   This section lists the alerts an implementation of this document
   sends, in addition to those already defined by TLS 1.3:

   *  illegal_parameter: a ServerHello or HelloRetryRequest that selects
      a KDF the client did not offer, a ServerHello whose
      schedule_profile differs from the HelloRetryRequest's, or a
      selected PSK whose KDF, for an imported PSK its target_kdf, is
      incompatible with the selected KDF.

   *  decrypt_error: a Finished or PSK binder MAC that fails
      verification, as in TLS 1.3.

   *  handshake_failure: a KDF of this document is required by local
      policy but none is negotiated.

13.  Companion Mechanisms

   Several deployed mechanisms invoke HKDF-Expand-Label or HMAC
   directly.  This document defines the Encrypted Client Hello
   confirmation for its KDFs (Section 5.7), because ECH is pervasive in
   the deployments most likely to exercise these schedules.  The
   remaining mechanisms are out of scope until a companion document
   defines their analogues.

13.1.  Out of Scope

   *  DTLS 1.3 [RFC9147] derives a record sequence-number encryption key
      (Section 4.2.3) and separates its schedule with the "dtls13" label
      prefix (Section 5.9).  DTLS-Only is N in Section 14.

   *  QUIC [RFC9001] derives its Initial secrets and its "quic key",
      "quic iv", "quic hp", and "quic ku" values with HKDF-Expand-Label.

   *  Exported Authenticators [RFC9261] compute their Finished value
      with HMAC under the connection's hash.

   An endpoint negotiating a KDF of this document MUST NOT use these
   mechanisms with that connection unless a specification defines their
   derivations for that KDF.

   This document requests no cipher suite code points.  It uses those of

14.2.  TLS KDF Identifiers

   IANA is requested to register two entries in the TLS KDF Identifiers

   A KDF registered here defines every key-schedule computation it
   governs: its transcript hash, its secret and key derivations, its

   of those to the cipher suite, as HKDF_SHA256 leaves its hash, has to

14.3.  Update to RFC 9258

   [RFC9258] anticipates this document: "Future specifications that
   change the way the KDF is negotiated will need to update this
   specification to make clear how target KDFs are determined for the
   import process."  This document changes how the KDF is negotiated,
   and determines target KDFs as follows.

   The target_kdf of an ImportedIdentity is the TLS KDF Identifier the
   importing client will negotiate in the schedule_profile extension
   (Section 6).  For a connection that negotiates no KDF, the target_kdf
   is HKDF_SHA256 or HKDF_SHA384 as the target cipher suite's hash
   determines, exactly as before this document.  For the KDFs defined
   here, Section 10 also replaces the importer computation and EPSK-
   associated-hash rule of Section 5.1 of [RFC9258].

   The schedule_profile extension carries the negotiated TLS KDF
   Identifier value on the wire, and the transcript hash covers it
   (Section 6), so no final message-level trace for a KDF of this
   document can exist before its value is assigned.  Schedule-level
   vectors do not wait on that assignment, since no derivation of
   Section 7.4 absorbs a code point: a transcript checkpoint enters as
   an argument, and one stated as a literal value pins the output with
   no code point anywhere in the input.  The exceptions are ipsk
   (Section 5.8), whose context is TranscriptHash of an ImportedIdentity
   that carries target_kdf, and values derived from ipsk, including the
   imported-PSK binder.  Appendix D carries no message-level trace yet.

15.  Security Considerations

15.1.  KDF Separation

   TLS13_TURBOSHAKE256 and TLS13_SHAKE256 frame the same schedule_label,
   so their inputs can coincide.  They run different permutations, the
   12-round Keccak-p[1600,12] and the 24-round Keccak-f[1600], though
   the first is the last 12 rounds of the second ([FIPS202], Sections
   3.3 and 3.4).  Most secret inputs are bound to a single KDF
   (Section 4).  For those secrets, coincident framed inputs do not by
   themselves expose either secret if both XOFs jointly behave as
   independent random oracles and the source-secrecy premises hold
   (Section 15.6).

   An external PSK used under both profiles is the exception.  For an
   imported PSK, Section 10 requires a separate ipsk per target_kdf, but
   the epsk beneath them is one secret, absorbed under both
   permutations.  Raw external PSK reuse also shares a secret between
   profiles.  A deployment that negotiates TLS13_SHAKE256 to avoid the
   reduced-round premise (Section 15.10.1) does not gain that separation
   for such a PSK.  A deployment that provisions a separate external PSK
   per KDF, rather than using one under both, has no secret in common
   between them.

15.2.  Downgrade Resistance

   The selected cipher suite appears in the ServerHello and therefore in
   the transcript from TH_SH onward, which every handshake and
   application output binds (Section 7.4).  A peer that assumed a
   different suite would hold a different transcript, and its Finished
   MAC would fail.

   Stripping the extension in flight makes the ClientHello transcripts
   differ and the Finished MACs fail.  A server can decline the
   extension by omitting it from the ServerHello (Section 6).  The
   client decides whether to accept that capability mismatch.  A
   deployment that offers both KDFs accepts whichever the server echoes.

15.3.  PSK Entropy

   An attacker who can guess an external PSK can recompute its binder
   offline.  External PSKs SHOULD be drawn with at least 512 bits of
   entropy, a conservative recommendation that bounds guessing in the
   random-oracle game by q / 2^512 in q queries (Section 15.6).  The
   512-bit capacity sets a 256-bit security target, rather than
   requiring 512 bits of PSK entropy.

15.4.  Authentication

   A fully SHA-2-free connection also needs SHA-2-free authentication.
   A deployment that must avoid SHA-2 entirely MUST restrict
   signature_algorithms and signature_algorithms_cert accordingly, or
   use PSK-only authentication.  Ed25519 uses SHA-512 internally, so the
   restriction excludes it in favor of Ed448, ML-DSA, or an SLH-DSA-
   SHAKE variant.

15.5.  Hybrid Key Exchange

   One high-entropy component keeps the derivation unpredictable even if
   another is adversarial.  This robustness relies on injective framing
   and the random-oracle argument (Section 15.8, Section 15.6,
   [BINDEL]), and on the source-secrecy and cross-stage simulation
   conditions left open in Section 15.6.4.

15.6.  Cryptographic Analysis

   The per-derivation bound comes from the sponge analysis ([BDPV08]),
   assuming source secrecy and the composition below.  Protocol security
   also depends on erasure and authentication, with proof obligations
   still open (Section 15.6.4).

15.6.1.  Threat Model and Goals

   The adversary model and key-schedule goals are those of [TLS13KS]: an
   active network adversary controls message delivery.  It may learn
   selected stage secrets under compromise predicates.  Authentication
   of peer identity remains outside the cipher suite, as in TLS 1.3.
   The schedule must provide indistinguishability of record keys and
   exporter outputs under the chosen AEAD, integrity of the handshake
   transcript through Finished and binder verification, forward secrecy
   from compromise of a handshake traffic secret to application traffic
   once the asymmetric shared secret is used, and the TLS 1.3 0-RTT
   replay model when early data is accepted.

15.6.2.  Primitive Assumptions

   DF is the profile's XOF over a framed byte string, its permutation
   modeled as random ([FIPS202]).  A sponge over such a permutation is
   indifferentiable from a random oracle up to 2^(c/2) of its calls
   ([BDPV08], Theorem 2 and Section 5), which is 2^256 at the 512-bit
   capacity both profiles use.

   The step from sponge to oracle is the indifferentiability composition
   of [MRH], which is sound for single-stage games and not in general
   for multi-stage ones ([RSS]).

   Every derivation is a single call DF(S, L) where seq(S) is
   injectively framed (Section 15.8), so distinct derivations query the
   oracle at distinct points.  In the random-oracle game, an adversary
   that never queries a string carrying the secret cannot distinguish
   those outputs from independent uniform strings.  For a secret with
   512 bits of entropy conditioned on its view, the chance of such a
   query is at most q / 2^512 in q queries (Section 15.3 covers a weaker
   external PSK).  These are bounds in that game, subject to the
   preceding composition step, not bounds for the complete protocol.

   Finished and binder verification require MAC to be unforgeable under
   a chosen-message attack.  Each MAC key is a 64-octet finished_key
   used for MAC and nothing else (Section 5.5).  The same key may be
   used over several messages, as for a binder recomputed after a
   HelloRetryRequest or for post-handshake Finished messages within one
   traffic generation.

   MAC is a Derive (Section 5.2), so the preceding random-oracle
   argument applies.  In that game, a uniform secret unknown to the
   adversary keys a pseudorandom function of the rest of the framed
   input.  With an L-octet output, each verification attempt adds at
   most 2^(-8L) to the forgery probability, in addition to the
   probability of querying the secret.

   The uniformity of finished_key to an adversary depends on that of the
   secrets beneath it.  A finished_key derived from a guessable external
   PSK is not uniform to the adversary (Section 15.3).

15.6.3.  Derivation Graph

   The stage trunks E, H, and T and the ratchet residues map to TLS
   1.3's Early/Handshake/Main Secrets and its unnamed "derived" salt as
   Section 7.4.2 sets out.  The map is onto rather than one to one: this
   document derives key_block once and slices the record key and IV from
   it, where TLS 1.3 derives each at its own site.  It is structural and
   does not carry the TLS 1.3 proof.

15.6.4.  What Is Not Yet Established

   This schedule does not yet have an analysis equivalent to [TLS13KS].

   The single-stage classification needed for [MRH]'s composition
   remains unproved ([RSS], Section 15.6).

   [TLS13KS] is proved over discrete extract-and-expand nodes, not over
   an accumulator carried across each stage and cloned at its leaves.
   The cross-stage chaining needs analysis, in particular absorbing the
   asymmetric shared secret into a deck seeded with the early residue,
   the step TLS 1.3 performs as an HKDF-Extract salted with the early
   secret's "derived" value.

15.7.  Erasure Boundaries

   A sponge accumulator is built on a permutation, and permutations are
   invertible.  If the intervening absorbed blocks are known, anyone
   holding a later state can recover the earlier one.  Carrying a raw
   accumulator across a stage boundary would therefore let a post-
   handshake state compromise re-derive handshake traffic secrets when
   those intervening blocks are known.

   A Ratchet breaks the chain because its squeeze returns a function of
   the state, not the state itself.  In the random-oracle game ([MRH]),
   recovering it requires a query on the secret-bearing input.  A
   boundary mixing an asymmetric shared_secret relies instead on the
   exchange's computational hardness and the open chaining analysis
   (Section 15.6.4), not on information-theoretic entropy given the
   public key shares.  The early-to-handshake boundary carries only the
   PSK, so its one-wayness depends on the PSK's min-entropy
   (Section 15.3): a low-entropy external PSK earns no forward secrecy
   there from the Ratchet alone.  A PSK-only handshake absorbs no
   asymmetric shared secret at all (Section 7.4.1), so every boundary
   has the same PSK-entropy limitation.

   The one-wayness argument is conditional on erasing the old trunk.
   The squeeze does not erase it.

   A ratchet's forward secrecy is only as good as the erasure behind it,
   and erasure is local: no peer observes it, and no interoperability
   test detects its absence.  The erasure rules below are therefore
   expectations, not interoperability requirements, and an
   implementation SHOULD follow them as its platform allows.

   An accumulator of a stage should not outlive that stage's ratchet,
   should not be retained as a successor across a ratchet, and should
   not be serialized, exported, or compared.  Handshake-stage traffic
   secrets and record keys should be destroyed when their TLS 1.3
   analogues would be, and each stage secret once the next stage has
   absorbed it.

   Every cloned accumulator is a 200-octet copy of secret state, and a
   clone exists for the span of a Derive.  Keeping that window short,
   and zeroizing each clone when it is dropped, limits what a compromise
   recovers.  Compromise of a live accumulator yields that stage's
   underived leaves, as compromise of a stage secret does in TLS 1.3.
   With the preceding state and other absorbed blocks known,
   invertibility can also expose an absorbed asymmetric shared secret.

   On platforms that cannot guarantee erasure these erasure rules are
   best effort (Appendix C).

15.8.  Domain Separation

   Distinct derivation paths yield distinct byte strings as deck-
   function inputs.  A framed sequence decodes to exactly one list of
   items: frame(x) is uint16(len(x)) || x with no padding (Section 2).

   Every deck opens with frame(schedule_label), then its rooting item
   (Section 7.1, Section 5.1): the PSK for the early stage, the early
   residue for the handshake stage, the handshake residue for the
   application stage, and the retained secret for a derivation
   (Section 7.4).  The PSK is framed under the tag "psk_" and every
   residue or retained secret under "seed", so the early trunk differs
   from every other deck in its first tag.  Decks that open with the
   same tag are told apart by their seed value and not by their
   structure.  A path over a live stage trunk and a path over a deck
   seeded with a retained secret draw from disjoint label vocabularies
   (Section 7.4, Section 7.2).  Within either, every item before the
   label is a framed tag drawn from this document's fixed vocabulary
   followed by its framed value, in an order the schedule fixes, so two
   paths of the same kind and the same length that agree tag for tag can
   differ only in a value.  Two paths that differ at all therefore
   differ at some item, so their framed sequences differ.

   Unkeyed transcript hashing is separated at the byte level:

   "tls13 hash"           = 0x74 0x6c ...

   frame(schedule_label)  = uint16(6) || "tls13 "
                          = 0x00 0x06 || "tls13 "

   The first octet separates a keyed sequence from the transcript hash.

15.9.  Related Constructions

   Proving Derive a pseudorandom function would discharge the
   pseudorandomness assumptions [TLS13KS] makes of its extract and
   expand functions and of the MAC deriving its binder values, though
   not its collision-resistance or salted Diffie-Hellman assumptions.
   No keyed-sponge result reaches this construction as specified.  The
   outer-keyed sponge is Sponge(K || m), the key first, with the
   analysis limited to keys occupying whole rate blocks ([KEYEDSPONGE]),
   where this schedule frames schedule_label ahead of a framed secret
   that does not fill a rate block.  Closing this needs a keyed-sponge
   result that tolerates a public prefix and a secret that does not fill
   a block, or a schedule that fits an existing one.

15.10.  Per-Profile Considerations

15.10.1.  TLS13_TURBOSHAKE256

   TLS13_TURBOSHAKE256 targets 256-bit security, which [RFC9861],
   Table 4 claims for TurboSHAKE256 and its 512-bit capacity ([RFC9861],
   Section 2.2) supports.  The 12-round assumption remains open.

15.10.2.  TLS13_SHAKE256

   TLS13_SHAKE256 uses SHAKE256's Keccak-f[1600] in place of
   TurboSHAKE256's Keccak-p[1600,12] (Section 9.1), so it carries no
   reduced-round assumption.  Its full 24-round permutation supports the
   same 256-bit target with a larger round margin (Section 9).

Appendix B.  Permutation-Counting Method

   This appendix is non-normative.

   For an input of n octets producing L octets, a sponge over the
   profile's permutation applies floor(n / 136) + 1 permutations while
   absorbing, since the padding rule always appends at least one octet,
   and ceil(L / 136) - 1 more while squeezing, since the first output
   block is read from the state the absorption left.

   Sibling leaves that bind one transcript checkpoint, a stage's traffic
   secrets, share its absorption.  Because the context precedes the
   label (Section 7.1), the running deck is cloned after the checkpoint
   is absorbed, so the checkpoint enters the permutation once for the
   stage and not once per leaf.

   Each HKDF-Extract, and each HKDF-Expand-Label of at most 32 octets,
   is one HMAC-SHA3-256, and one HMAC-SHA3-256 is four permutation
   calls: two for the inner hash of (K XOR ipad) || m and two for the
   outer hash of (K XOR opad) || digest, each filling one 136-octet
   block and padding into a second.

   TLS 1.3 with KMAC ([SP800-185]) in place of HMAC, for extraction,
   expansion, and the MAC, spends 90 permutation calls, three for each
   of the same 30 invocations.  KMAC runs one cSHAKE where HMAC nests
   two hashes, but each call still absorbs a bytepad-framed
   customization block and a bytepad-framed key block before its
   message, so it saves one of HMAC's four permutations and not two.

Appendix C.  Implementation Considerations

   This appendix is non-normative.

   Both profiles need the same three capabilities of an XOF: incremental
   absorption, cloning of a state that has not produced output, and a
   squeeze of a length known before the squeeze begins.  Each profile's
   concrete parameters are in Section 8.1 and Section 9.1.

   Each handshake and application leaf absorbs its transcript
   checkpoint, TH_SH, TH_SF, or TH_CF, as its Derive context
   (Section 7.4), the same point at which the corresponding TLS 1.3
   Derive-Secret call consumes Messages.  A stack ported from TLS 1.3
   therefore need not compute any transcript checkpoint it does not
   already compute.

   A client that offers PSKs associated with different KDFs computes
   each binder under its own PSK's KDF, and therefore maintains
   transcript-hash state per KDF for the partial ClientHello transcript.
   TranscriptHash is itself defined by the KDF (Section 8.1,
   Section 9.1), so the checkpoints of Section 2.1 differ per offered
   KDF.  A client offering more than one either buffers the handshake
   messages until the KDF is known or carries checkpoint state per
   offered KDF, discarding the state of those not selected once the KDF
   is pinned, at the ServerHello or at a HelloRetryRequest.  This is the
   one place where offering more than one KDF costs an implementation
   more than a single schedule: the schedule binds no cipher suite
   (Section 7.4), so it is shared across every suite offered, and only
   the record-key output lengths depend on the suite (Section 5.3).

   A binder and a Finished derive their MAC key from different base
   secrets, binder_key against a handshake traffic secret, though both
   derive it under "fin" (Section 5.5).  An implementation that feeds a
   binder's MAC key from the Finished path's base secret produces a
   wrong binder that no Finished-path test vector detects.

   In garbage-collected runtimes, zeroization is inherently best effort:
   the runtime may have copied or moved key material, and erasing every
   copy is not achievable from the language.  The erasure rules of
   Section 15.7 are written to be met on such platforms by ceasing use,
   dropping references, and zeroizing the buffers the implementation
   controls, as implementations already do for TLS 1.3 key material.

Appendix D.  Test Vectors

   This appendix is non-normative.

   The vectors below are tentative.  They were produced by a reference
   implementation and reproduced byte for byte by a second
   implementation written from this document alone, in another language
   and sharing no code with the first, but written by the same author.
   They are therefore not yet the independent evidence this appendix
   calls for, and they may change.  Each profile's permutation is pinned
   against published vectors, TurboSHAKE256 against those of [RFC9861]
   and SHAKE256 against those of [FIPS202].  What rests on a single
   reading of this document is the schedule itself: the framing, the
   field order, and the context tags.  That is the part most likely to
   move.

   Every secret and checkpoint is TranscriptHash of a short ASCII
   string, so the inputs are reproducible from this document and the
   same values serve as TranscriptHash vectors:

   PSK           = TranscriptHash("psk")
   shared_secret = TranscriptHash("asymmetric shared secret")
   hybrid_1      = TranscriptHash("hybrid component 1")
   hybrid_2      = TranscriptHash("hybrid component 2")
   epsk          = TranscriptHash("epsk")
   TH_CH0        = TranscriptHash("truncated ClientHello")
   TH_CH         = TranscriptHash("ClientHello")
   TH_SH         = TranscriptHash("ClientHello..ServerHello")
   TH_PRE_SF     = TranscriptHash("ClientHello..before server Finished")
   TH_SF         = TranscriptHash("ClientHello..server Finished")
   TH_CF         = TranscriptHash("ClientHello..client Finished")

   checkpoints.  The PSK-only fixture omits Absorb(H, "shs_", ...)
   entirely (Section 7.4.1).  The hybrid fixture absorbs hybrid_1 and
   hybrid_2 in that order, with a separate Absorb(H, "shs_", component)
   call for each and no concatenation (Section 7.4).

   The server Finished uses TH_PRE_SF, the checkpoint immediately before
   that message.  TH_SF includes the server Finished and remains the
   checkpoint for application traffic and exporter secrets.  A client
   Finished would use TH_SF if no handshake messages, including client
   authentication messages, intervene.  These checkpoints are synthetic
   inputs, not hashes of encoded handshake messages.

   ClientHelloInner.random is the 32 octets 0x00 through 0x1f, and the
   ECH confirmations take TranscriptHash("ech_conf_messages") and
   TranscriptHash("hrr_ech_conf_messages") as their transcript hashes.
   Record keys use Nk = 16 and Nn = 12.  The exporters use label "test
   label" and context "test context" with a 32-octet output.  The two
   resumption values use ticket_nonce "nonce" and an empty ticket_nonce,

   ImportedIdentity has external_identity "external psk identity", an

Appendix E.  The NIST Shapes of the TLS 1.3 Key Schedule (Informative)

   This appendix is non-normative.

     +=======================+=====================+=================+

      Table 7: TLS 1.3 Key-Schedule Sites, This Document, and the NIST
                       Recommendation for Each Shape

   TLS13_SHAKE256 computes every value, its MACs included, with
   SHAKE256, an approved function of [FIPS202], but in a construction no
   Special Publication specifies.  A deployment that requires approved
   components cannot use either KDF of this document.

   [SP800-56C], Table 4 permits HMAC-SHA3-256, so the one conformant
   SHA-3-family schedule today is HMAC-SHA3 in the extraction and
   expansion rows: TLS 1.3 with a SHA-3 hash, which changes the hash and
   not the schedule.

   [SP800-56C], Section 8.3: "At this time, KMAC has not been specified
   for use in the implementation of a two-step key-derivation procedure.
   This restriction may be reconsidered once a KMAC-based KDF has been
   approved for use as a PRF-based KDF in a revision of [SP 800-108]."
   That revision exists: [SP800-108] is Revision 1, and its own account
   of what changed reads "In Revision 1, a KDF using KMAC is added in
   Section 4.4".  The condition NIST named has been met.
