XOF-based key schedules for TLS 1.3

Abstract

TLS 1.3 runs its entire key schedule on HKDF over SHA-2. This document defines an extension that replaces that schedule with one built on an extendable-output function (XOF): the negotiated KDF governs every derivation, the Finished and binder MACs, and the transcript hash, so no SHA-2 remains in the key schedule. The cipher suites, AEAD algorithms, state machine, and record layer are unchanged, and a connection without the extension uses HKDF as today. Two KDFs are defined, SHAKE256 and the reduced-round TurboSHAKE256. This document updates RFC 9147, RFC 9258, RFC 9261, and RFC 9849.¶

1. Introduction

In TLS 1.3 [RFC9846], every cipher suite runs its key schedule on HKDF over the suite's hash. This document defines an extension that negotiates an XOF-based KDF for the connection. Its key schedule runs on a single Keccak permutation and replaces HKDF across every derivation, the Finished and binder MACs, and the transcript hash. The permutation is the one a deployment already carries when it uses SHA-3, ML-KEM, or ML-DSA. When no KDF is negotiated, the cipher suite's hash names HKDF and TLS 1.3's own schedule runs, exactly as today. Instantiating HKDF with a SHA-3 hash would remove SHA-2 without changing how the schedule works. This document changes the schedule itself, not the hash.¶

TLS 1.3 already negotiates groups, KEMs, signature schemes, PSKs, and AEAD algorithms. This document extends that agility to the key schedule itself. A TLS 1.3 cipher suite identifies an AEAD algorithm and the hash used with HKDF. This document leaves the suite alone and negotiates the KDF beside it:¶

A KDF (Section 3) defines every key-schedule computation the connection uses: the transcript hash, the secret and key derivations, the Finished and PSK binder MACs, and the Encrypted Client Hello acceptance computations. It is negotiated in the schedule_profile extension of Section 6, independently of the cipher suite. A connection that negotiates no KDF is a TLS 1.3 connection: absence is the default, and TLS 1.3's own schedule needs no identifier of its own.¶

Each KDF defined here is a profile of the same deck function. This extendable-output function absorbs the schedule's inputs as length-framed strings and squeezes each derived value from the accumulated sequence. It is defined once for both profiles in Section 7, and each selects a different permutation for it: TLS13_TURBOSHAKE256 (Section 8) uses the 12-round TurboSHAKE256 [RFC9861], and TLS13_SHAKE256 (Section 9) uses the 24-round SHAKE256 [FIPS202]. Finished and PSK binder values, including an Exported Authenticator's Finished, use one MAC (Section 5.2). The Encrypted Client Hello acceptance value is produced by the deck's output operation, Derive (Section 5.7).¶

1.1. Design Goals

A KDF turns the whole derivation surface of a connection into one named, testable object. Every value comes from one permutation, every query is injectively framed (Section 7.1), DeriveN outputs occupy disjoint slices, and Appendix D gives byte-exact values for both profiles. Neither KDF uses SHA-2, HMAC, or HKDF in any role, and the correspondence with TLS 1.3 can be audited shape by shape (Section 7.3).¶

The alternative is to keep TLS 1.3's HKDF schedule and give it a SHA-3 hash.¶

The deck costs fewer permutation calls than that alternative. HKDF is built on HMAC, and every HMAC call nests two hash calls, overhead that exists only to key a hash not built for keying. A keyed sponge needs no such wrapper: it produces each Derive output in one squeeze, with no separate extract step between stages.¶

Over the representative handshake of Appendix A, the deck costs 23 Keccak permutation calls against 120 for a hash-only HKDF-SHA3-256 over the same permutation (Appendix A.2). HMAC accounts for four permutation calls in every HKDF operation, two for each of its nested hashes, where a Derive here costs one or two and a DeriveN at most three (Appendix B).¶

1.2. Scope

This document does not define a new version of TLS, and defines no cipher suites. It adds one extension. The state machine, record layer, all other wire structures, cipher suites, AEAD algorithms, and per-record nonce construction remain those of TLS 1.3, or of DTLS 1.3 on a DTLS 1.3 connection (Section 14.1).¶

A KDF governs only the key schedule and the transcript hash (Section 6.1). Negotiating one does not by itself make a connection free of SHA-2: certificate-based authentication is negotiated separately and commonly relies on SHA-2 (Section 12). A deployment that requires a fully SHA-2-free TLS or DTLS connection must additionally restrict itself to SHA-2-free signature schemes and certificate chains, or use PSK-only authentication. Note also that the cipher suite continues to name a hash, which under a KDF of this document governs nothing in the key schedule (Section 6.1).¶

1.3. Deck Functions

A key schedule is a derivation tree. A deck function (Section 7.1) expresses that tree directly: absorb a stage's inputs into a running accumulator, derive each leaf from a clone, and ratchet the accumulator into the next stage. One XOF does the work HKDF splits between Extract, at the stage boundaries, and Expand-Label, at the leaves.¶

The construction takes no key: a secret is an ordinary framed input. The operations named here, Init, Absorb, Derive, DeriveN, and Ratchet, are defined normatively in Section 7.¶

2. Conventions and Definitions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

This document uses the following terms.¶

KDF:

The key-derivation function of a connection, named by a TLS KDF Identifier and negotiated in the schedule_profile extension (Section 6). It defines every key-schedule computation of the connection (Section 3) and determines the key schedule: a TLS13_TURBOSHAKE256 or TLS13_SHAKE256 identifier implies this document's deck schedule (Section 7), and absence of the extension implies TLS 1.3's HKDF schedule over the cipher suite's hash.¶

selected_cipher_suite:

The cipher suite selected in the ServerHello message, as a 16-bit integer. uint16(selected_cipher_suite) yields its two-octet TLS 1.3 encoding.¶

associated cipher suite:

The cipher suite associated with a PSK (Section 4).¶

trunk (stage trunk):

The running deck accumulator for a schedule stage (E, H, or T), which absorbs the stage's inputs, is cloned for each of the stage's leaf outputs or DeriveN output tuples, and yields an internal squeezed residue that seeds the next stage's trunk at the stage boundary.¶

shared_secret:

The asymmetric shared secret, computed as in Section 7.4 of [RFC9846].¶

Nk, Nn:

The AEAD key and nonce lengths of the selected cipher suite, in octets.¶

FLen:

The length of the verify_data of a Finished message, including an Exported Authenticator's, and of a PSK binder: 64 octets in both profiles of this document.¶

uint16(n):

The two-octet big-endian encoding of n, as in the TLS presentation language.¶

||:

Octet-string concatenation.¶

x[a..b]:

Octets a through b-1 of the octet string x, indexed from zero.¶

frame(x):

uint16(len(x)) || x, where len(x) is the octet length of x.¶

Strings are length-prefixed only: they are not null-terminated or otherwise padded after x. Both profiles of this document build every derivation input from framed items, so inputs are injectively encoded.¶

A uint16 encodes 65535, so frame(x) carries any x of 0xFFFF octets or fewer, and longer inputs do not occur: variable-length public values are reduced by the transcript hash or explicitly bounded before framing, and the one variable-length secret input, an external PSK, is bounded by Section 10.¶

An empty value contributes frame("") wherever it is framed, encoding as the two octets 0x0000 with no payload octets. An absent input omits its framed items entirely. Omitting an input is not the same as framing an empty value.¶

2.1. Transcript Hash

The transcript hash is an unkeyed 64-octet hash defined by the negotiated KDF (Section 8, Section 9). TranscriptHash is computed over the handshake transcript as in Section 4.1 of [RFC9846]: message type and length fields are included, and record-layer framing is excluded. TranscriptHash accepts any octet string. The TLS 1.3 rules define only how the handshake transcript is serialized before hashing, and the same function is applied to non-transcript inputs such as exporter contexts and imported PSK identities. For a HelloRetryRequest, the synthetic-message construction in Section 4.1 of [RFC9846] is retained, substituting TranscriptHash for Hash.¶

In both profiles of this document, TranscriptHash takes no cipher suite input, so a client can compute its checkpoints before the ServerHello. The selected suite enters the transcript at the ServerHello, separating later outputs as in TLS 1.3. The schedule_profile extension enters the transcript at the ClientHello, so TH_CH0, TH_CH, and TH_SH bind the offered KDFs.¶

This document uses the following checkpoint values:¶

TH_CH0:

TranscriptHash of the partial ClientHello transcript in Section 4.3.11.2 of [RFC9846]: the handshake messages through the ClientHello, with the ClientHello truncated after the PreSharedKeyExtension.identities field and the binders list excluded. After a HelloRetryRequest, this partial transcript includes the first ClientHello and the HelloRetryRequest via the synthetic-message construction of Section 2.1, exactly as in TLS 1.3.¶

TH_CH:

TranscriptHash(ClientHello).¶

TH_SH:

TranscriptHash(ClientHello up to and including ServerHello).¶

TH_SF:

TranscriptHash(ClientHello up to and including the server Finished message).¶

TH_CF:

TranscriptHash(ClientHello up to and including the client Finished message).¶

For a Finished MAC computed by either peer, the covered transcript is taken up to but not including the Finished message being computed, consistent with Section 4.5.3 of [RFC9846].¶

3. Key-Derivation Functions

A KDF is a set of algorithms and encodings negotiated in the schedule_profile extension (Section 6), independently of the cipher suite. A KDF specifies:¶

  • the XOF over which its deck schedule and MAC are instantiated (Section 7).¶

  • SecretLen, the length of stage and traffic secrets.¶

  • FLen, the length of Finished and binder verify_data.¶

  • TranscriptHash(messages), the unkeyed transcript hash of Section 2.1.¶

  • the derivation of initial and stage secrets from PSK and key-exchange inputs (an extract operation, a stage accumulator, or an equivalent construction).¶

  • the derivation of every handshake, application, exporter, and resumption secret.¶

  • the Finished MAC and PSK binder computations.¶

  • record key and IV derivation.¶

  • traffic-secret update.¶

  • exporter derivation.¶

  • resumption PSK derivation.¶

  • the Encrypted Client Hello acceptance computations.¶

  • the domain-separation and input-framing rules its derivations use.¶

The suite continues to select the AEAD, as in Section 4.2 of [RFC9846]. Future specifications may define additional KDFs by registering a TLS KDF Identifier (Section 15) whose definition covers every computation listed above.¶

Every derivation of a KDF MUST bind at least the following into the input of the underlying primitive: a protocol identifier (the KDFs of this document frame schedule_label, Section 7), each output label and length (a KDF MAY instead fix the length of an internal stage secret as a constant, provided the operation that produces it is domain-separated from every variable-length operation), the transcript checkpoint or other public context where applicable, and the secret input or the stage that carries it. All variable-length items MUST be length-framed. A multi-output operation also MUST bind the output count and ordered partition. Distinct canonical input sequences have distinct encodings. Outputs of one DeriveN share a query and occupy disjoint slices (Section 16.8).¶

Both profiles of this document bind each output length as uint16. DeriveN also bounds their sum to 65535 octets (Section 7.1), so no invocation produces more than 65535 octets. The exporter is the one derivation whose length is caller-chosen, and Section 5.6 says which requests it rejects. Every other output length in this document is fixed: a profile constant, Nk, Nk + Nn, or the 8 octets of an ECH confirmation, and each fixed DeriveN total is a sum of these. All are far below the bound.¶

4. KDF Selection and PSK Compatibility

The negotiated KDF governs the whole key schedule of a connection, the role SHA-256 or SHA-384 plays in Section 7.1 of [RFC9846]. Its XOF runs every derivation of the schedule (Section 7).¶

A PSK binder is computed before the server selects a cipher suite, and verified under the KDF the PSK is bound to. As in Section 4.3.11 of [RFC9846], a server MUST verify the binder of any PSK it selects. The binder is keyed by a secret derived under that KDF (Section 5.5), so a binder computed under one KDF verifies under another only by chance.¶

A server MUST NOT select a PSK unless the KDF of the connection it forms is compatible with the KDF associated with the PSK. Two KDFs are compatible only if they are the same TLS KDF Identifier. This document defines no broader compatibility. This rule is the analogue of Section 4.3.11 of [RFC9846], which requires a resumption to share the PSK's hash: under this document the KDF is the hash (Section 6.1). A client MUST abort the handshake with an illegal_parameter alert if the server selects a PSK whose KDF is incompatible with the selected KDF, as that section requires of the hash.¶

Otherwise a 1-RTT resumption follows TLS 1.3. The selected cipher suite need not equal the PSK's associated cipher suite. A resumption MAY change the AEAD as long as the KDFs are compatible. The selected suite appears in the ServerHello and therefore in the transcript, which separates every handshake and application output as in TLS 1.3 (Section 16.2).¶

After a HelloRetryRequest, an updated binder remains under the PSK's KDF. A client SHOULD omit from its updated ClientHello any PSK whose KDF is incompatible with the KDF implied by the HelloRetryRequest, and MUST recompute binders as required by Section 4.3.11.2 of [RFC9846].¶

For 0-RTT, the server MUST require the selected cipher suite to equal the PSK's associated cipher suite (Section 11). This is TLS 1.3's own 0-RTT rule.¶

A PSK that is offered but not selected contributes no secret to the schedule, though its identity and binder remain in the ClientHello and so in the transcript. If the server does not select the client's PSK, both peers compute the connection's schedule as a handshake without a PSK: the client discards any PSK-keyed schedule state it built for the binder or for early data, along with its outputs, and begins the schedule again with the empty PSK, applying the destruction rules of its KDF.¶

Implementations MUST associate every PSK and session ticket with its KDF to select a compatible PSK and compute its binder. For an imported PSK, this is its target_kdf (Section 10). Implementations MUST also retain the PSK's associated early-data parameters (cipher suite, ALPN, and early-data permission). As in Section 4.3.10 of [RFC9846], these are provisioned along with the key for external PSKs, including imported PSKs, and negotiated when the PSK was established for resumption PSKs and session tickets. An imported PSK without provisioned early-data parameters is not eligible for early data.¶

5. Keyed Derivations

Every derivation in this document that is keyed by a retained octet-string secret, rather than by a live stage of a profile's schedule, is a deck session rooted at that secret (Section 7), specified once for both profiles in Section 5.1 since the deck is identical up to its permutation. MAC, which computes the Finished and PSK binder tags, is one such derivation (Section 5.2). The stage schedule is also the same for both profiles (Section 7.4), and only DF differs (Section 8, Section 9).¶

5.1. Deriving from a Retained Secret

A value keyed by a retained octet-string secret uses Derive or DeriveN (Section 7.1) whose deck is seeded with that secret rather than run as a live stage trunk. The seed is the secret itself: Init(secret), the same way a ratchet seeds the next stage with its residue. Derive then adds the context under the "ctx_" tag if any, the label, and the output length under the "out_" tag:¶

D     = Init(secret)                # Init frames schedule_label, "seed"
value = Derive(D, label, [context], [L])

(o_1, ..., o_k) =
    DeriveN(D, [(label_1, L_1),
                ...,
                (label_k, L_k)], [context])
¶

label is a 3-octet label registered in the TLS XOF Key Schedule Labels registry (Section 15.3), whose initial contents are the labels of Section 7.2, context is an octet string, and L is the output length in octets. Every item is length-framed by the deck (Section 16.8). DeriveN binds the ordered labels and lengths before one squeeze and partitions that output into disjoint slices. An empty context is omitted rather than framed as an empty value, and omission is its canonical encoding. It differs from an explicitly framed empty value, because after an omitted context the next item is the label or "outs", not frame("ctx_"). L never exceeds 65535 octets (Section 3). Such a Derive is the analogue of TLS 1.3's HKDF-Expand-Label, and Section 7.2 gives the label each of its labels replaces in TLS 1.3 or DTLS 1.3.¶

The following retained-secret derivations are instances of this shape, each fixing the base secret, label, context, and output length. The exporter (Section 5.6) uses two such derivations, with the raw exporter label as the first context and the context hash as the second. The ECH acceptance confirmations (Section 5.7) take a transcript hash as context, and MAC (Section 5.2) takes the message it authenticates. Every derivation of this shape carries its context under the "ctx_" tag, including one whose context is itself a transcript hash.¶

  1. Early key_block (Section 5.3) uses c_e_traffic as its base secret, label "key", no context, and length Nk + Nn in a single-output Derive.¶

  2. The DeriveN that derives finished_key and key_block (Section 5.3) uses the sender's handshake traffic secret as its base secret and no context. Its outputs are finished_key with label "fin" and length SecretLen, then key_block with label "key" and length Nk + Nn.¶

  3. The DeriveN that derives the next traffic secret and key_block (Section 5.4) uses the sender's current application traffic secret as its base secret and no context. Its outputs are the next traffic secret with label "upd" and length SecretLen, then key_block with label "key" and length Nk + Nn.¶

  4. resumption_psk uses resumption_secret as its base secret, label "rsp", context ticket_nonce, and length SecretLen in a single-output Derive.¶

  5. ipsk (Section 5.8) uses epsk as its base secret, label "ipk", context TranscriptHash(ImportedIdentity), and length SecretLen in a single-output Derive. The context is the transcript-hash reduction defined in Section 5.8.¶

The DeriveN calls for record keys apply separately to each direction. "key" names the whole key_block, which contains write_key followed by write_iv.¶

5.2. MAC

MAC(key, message, L) computes every tag in this document: the PSK binder, both Finished values, and the Finished of an Exported Authenticator (Section 14.2). It is a Derive over a deck seeded with the key (Section 5.1), with the label "mac" and the message as its context:¶

MAC(key, message, L) = Derive(Init(key), "mac", message, L)
¶

Every MAC of this document takes a 64-octet key and a 64-octet transcript hash as its message, so its input to DF (Section 7.1) is these 167 octets, with the key and the message each starting on an 8-octet boundary (Section 7.2). The listing is the TLS 1.3 layout. A DTLS 1.3 connection substitutes "dtls13" for "tls13 ", with the same lengths and offsets (Section 14.1):¶

offset
     0  0x0006 || "tls13 "    frame(schedule_label), from Init
     8  0x0004 || "seed"      frame("seed")
    14  0x0040 || key         frame(key), at offset 16
    80  0x0004 || "ctx_"      frame("ctx_")
    86  0x0040 || message     frame(message), at offset 88
   152  0x0003 || "mac"       frame("mac"), the label
   157  0x0004 || "out_"      frame("out_")
   163  0x0002 || uint16(L)   frame(uint16(L))
¶

No other derivation of this document uses the label "mac", so a MAC input is never the input of another derivation (Section 16.8). The output length is bound by the "out_" item as in every Derive, so tags of different lengths are computed over different inputs. MAC is the analogue of TLS 1.3's HMAC-based Finished and binder MACs, and like them it is keyed by a dedicated key that keys nothing else (Section 5.5, Section 14.2). The client and server Finished values are computed the same way, each over a different key and a different message. L never exceeds 65535 octets (Section 3).¶

MAC uses the profile's DF and nothing else, so it needs no primitive beyond the SHAKE256 [FIPS202] or TurboSHAKE256 [RFC9861] that computes every other derivation and the transcript hash.¶

5.3. Record Keys

Record keys are the "key" output of Section 5.1. A retained traffic secret suffices to re-derive its keys, as in TLS 1.3. For early-data keys, derived before the ServerHello, Nk and Nn are those of the offered PSK's associated cipher suite. For every other traffic secret they are those of selected_cipher_suite.¶

Early record keys use the single-output encoding:¶

# no context, so the third argument is the output length
key_block = Derive(Init(c_e_traffic), "key", Nk + Nn)
write_key = key_block[0..Nk]
write_iv  = key_block[Nk..Nk+Nn]
¶

Each handshake traffic secret uses a fixed DeriveN call that also produces that sender's Finished key:¶

(finished_key, key_block) =
    DeriveN(Init(hs_traffic_secret), [("fin", SecretLen),
                                      ("key", Nk + Nn)])

write_key = key_block[0..Nk]
write_iv  = key_block[Nk..Nk+Nn]
¶

Every application traffic-secret generation uses a fixed DeriveN call that also produces the next generation's secret:¶

(app_traffic_secret_{N+1}, key_block_N) =
    DeriveN(Init(app_traffic_secret_N), [("upd", SecretLen),
                                         ("key", Nk + Nn)])

write_key_N = key_block_N[0..Nk]
write_iv_N  = key_block_N[Nk..Nk+Nn]
¶

The application record DeriveN runs even when no KeyUpdate is planned, so the next traffic secret exists from the start of its predecessor's epoch. The next generation's record keys are derived only when its epoch starts.¶

SecretLen is 64, so the secret and key_block start on 64-bit boundaries, and the IV does too when Nk is a multiple of 8. Each descriptor's length is bound into the input. The split is unambiguous: Nk and Nn are fixed by the suite, and their sum is bound into the derivation as the key_block output length, so Nk + Nn also changes the finished_key or next traffic secret derived alongside it. The traffic secret is already specific to one direction and one stage, so no direction or epoch input is needed. The per-record nonce construction, record format, and AEAD additional data are unchanged from TLS 1.3, or from DTLS 1.3 on a DTLS 1.3 connection.¶

5.4. Key Update

A key update installs app_traffic_secret_{N+1}, the "upd" output already produced with generation N's record keys (Section 5.3). It then runs the application record DeriveN again, under the installed secret:¶

# next_secret is the "upd" slice retained from generation N
app_traffic_secret_{N+1} = next_secret

(next_secret, key_block_{N+1}) =
    DeriveN(Init(app_traffic_secret_{N+1}), [("upd", SecretLen),
                                             ("key", Nk + Nn)])

write_key_{N+1} = key_block_{N+1}[0..Nk]
write_iv_{N+1}  = key_block_{N+1}[Nk..Nk+Nn]
¶

The new next_secret is app_traffic_secret_{N+2} and is retained until the next update.¶

An implementation MUST NOT derive generation N+1 from anything other than generation N, in particular not from a retained stage accumulator or a counter: that rule determines the derived value and so is an interoperability requirement. Each generation is also an erasure boundary. In TLS, the previous secret, its keys, and any schedule state derived from them are destroyed once the new generation is installed, except for the successor secret deliberately carried across the boundary (Section 16.7). In DTLS, a receiver MUST retain the previous epoch's record key, IV, and sn_key (Section 14.1), or their traffic secret, until it successfully decrypts a record from the new epoch (Section 8 of [RFC9147]).¶

5.5. Finished and PSK Binder MACs

Finished and PSK binder verify_data are computed under a dedicated MAC key, derived from a stage or traffic secret (Section 5.1), rather than by MACing that secret directly. This matches Section 4.5.3 of [RFC9846]: finished_key and binder_key take the roles of TLS 1.3's identically named intermediates, and MAC takes the role of TLS 1.3's HMAC.¶

A handshake finished_key is the "fin" output of the DeriveN that derives that sender's handshake record keys (Section 5.3).¶

# For post-handshake authentication only:
finished_key = Derive(Init(base_key), "fin")

# For every Finished:
verify_data = MAC(finished_key, th, FLen)
¶

For post-handshake authentication, base_key is the sender's current application traffic secret from the authentication-input table of Section 4.5 of [RFC9846]. The label is "fin", and th covers the Handshake Context and authentication messages that the same table gives for that Finished, up to but not including the Finished being computed. For a PSK binder, the dedicated key is derived in two steps, as TLS 1.3 derives binder_key in Section 7.1 and then finished_key from it in Section 4.3.11.2, via Section 4.5.3:¶

(binder_key, early_residue) =
    DeriveN(E, [(binder_label, SecretLen),
                ("drv",        SecretLen)])

finished_key = Derive(Init(binder_key), "fin")
verify_data  = MAC(finished_key, TH_CH0, FLen)
¶

E is the live early trunk of the schedule keyed by that PSK, before its ratchet (Section 7.4). binder_key comes from a DeriveN on E that also derives early_residue, so the early trunk is the analogue of TLS 1.3's Early Secret from which Section 7.1 of [RFC9846] derives binder_key. binder_label is "ebk" for a non-imported external PSK, replacing "ext binder", "ibk" for an imported PSK, replacing "imp binder" from Section 5.2 of [RFC9258], and "rbk" for a resumption PSK, replacing "res binder".¶

The handshake deck is seeded from this DeriveN (Section 7.4), so the early residue depends on the binder label, so equal non-imported external, imported, and resumption PSK bytes lead to different handshake-stage inputs. Without a PSK there is no binder DeriveN.¶

finished_key is derived under "fin" for both a Finished and a binder, and the two are already separated one step up by their base secret, a traffic secret against binder_key. Both finished_key and binder_key are 64 octets, the length of every stage and traffic secret in both profiles (SecretLen, Section 8, Section 9), matching TLS 1.3's use of Hash.length for the same intermediates. Binder verification follows Section 4.¶

Appendix A counts every finished_key and binder_key derivation of a representative full handshake against the corresponding TLS 1.3 HKDF-Expand-Label calls.¶

Each finished_key is a dedicated MAC key, and a handshake Finished MAC key shares its base secret, the sender's handshake traffic secret, with that sender's record keys (Section 5.3).¶

Binders are computed before the ServerHello. This is possible in both profiles because the early trunk binds no cipher suite: the client clones the early trunk to obtain binder_key at ClientHello time, in either profile (Section 7).¶

5.6. Exporters

Exporters use two retained-secret derivations, following the shape of Section 7.5 of [RFC9846]:¶

TLS-Exporter(label, context, length):
    exporter_label_secret = Derive(Init(exporter_secret), "exl",
                                   label, SecretLen)
    return Derive(Init(exporter_label_secret), "exp",
                  TranscriptHash(context), length)
¶

The early exporter is the same construction keyed by early_exporter_secret. The raw label is the first Derive's context and is framed under "ctx_" (Section 5.1). An implementation MUST reject a TLS-Exporter request whose label exceeds the 65535-octet frame limit, rather than reduce its length modulo 65536.¶

The intermediate lets an implementation that knows all its exporter labels derive their label secrets and then erase exporter_secret, as Appendix F.1.4 of [RFC9846] recommends.¶

Framing the raw label separates inputs to the first Derive without relying on TranscriptHash collision resistance for that separation. The second Derive takes the context hash because the context has unbounded length. An implementation MUST reject a TLS-Exporter request for zero octets or for more than 65535 octets of output. Reducing a longer request modulo 65536 would let two different requested lengths bind the same encoded value.¶

This document updates [RFC9849] for a connection that negotiates a KDF of this document. A connection that negotiates no KDF uses [RFC9849] unchanged. For the KDFs of this document, the ECH acceptance signals of [RFC9849] are:¶

replacing the HKDF-Extract and HKDF-Expand-Label computations of [RFC9849] and its labels "ech accept confirmation" and "hrr ech accept confirmation", with ech_conf_messages and hrr_ech_conf_messages the handshake message ranges that document identifies for each confirmation, per Section 4.1 of [RFC9846]. TranscriptHash(ech_conf_messages) is the transcript_ech_conf of [RFC9849], the same single transcript-hash operation, applied once.¶

5.8. PSK Import Derivation

An external PSK is imported per target KDF (Section 10). For every KDF of this document, ipsk is the "ipk" derivation of Section 5.1, keyed by epsk with TranscriptHash(ImportedIdentity) as context, with target_kdf as the KDF. This follows the shape of the derivation in [RFC9258], with the entire serialized ImportedIdentity reduced by the transcript hash as the context. ipsk is an explicit octet string by design: it crosses a system boundary into the PSK store. epsk is absorbed as the secret of a deck derivation (Section 5.1) in both profiles, so a low-entropy or attacker-influenced epsk never keys either profile's underlying permutation directly.¶

6. Negotiating a KDF

This document defines no cipher suites. A connection uses the cipher suites of TLS 1.3, and negotiates its KDF separately, in a new extension.¶

Coupling the two would make the offered set the product of the AEAD choices and the schedule choices, and would oblige a client that wants one schedule with two AEADs to carry a code point for each combination. The schedule and the AEAD are independent choices, and this document negotiates them independently.¶

The value negotiated is a TLS KDF Identifier, the registry [RFC9258] already created for naming a key schedule independently of a cipher suite. A KDF of this document registers there (Section 15).¶

struct {
    uint16 profiles<2..2^16-2>;   /* TLS KDF Identifiers */
} ScheduleProfileList;
¶

The extension_data of a schedule_profile extension (Section 15) is a ScheduleProfileList in a ClientHello, in preference order, and a single uint16 in a ServerHello or a HelloRetryRequest.¶

Absence is the default, and the default is TLS 1.3: a connection whose ClientHello omits the extension, or whose server does not echo it, runs the key schedule in Section 7.1 of [RFC9846], HKDF over the negotiated cipher suite's hash. That is HKDF_SHA256 or HKDF_SHA384 as the suite's hash determines, so TLS 1.3's own schedule needs no value of its own here and an endpoint of this document interoperates with TLS 1.3 unchanged.¶

A client that requires an alternative schedule MUST abort with a handshake_failure alert if the ServerHello omits the extension (Section 16.2). The offered list does not signal whether the client requires an alternative schedule or permits fallback. Because absence is the sole signal for the TLS 1.3 schedule, a ScheduleProfileList MUST NOT include HKDF_SHA256 or HKDF_SHA384, the other values of the TLS KDF Identifiers registry ([RFC9258]). A server that receives either MUST treat it as if that KDF were not offered, and MUST NOT select it.¶

The KDFs of this document are TLS13_TURBOSHAKE256 (Section 8) and TLS13_SHAKE256 (Section 9).¶

A server MUST NOT select a KDF the client did not offer. A client that sent schedule_profile MUST abort the handshake with an illegal_parameter alert if the ServerHello or HelloRetryRequest selects a KDF it did not offer, as Section 4.2.3 of [RFC9846] requires for the cipher suite. A client that did not send it treats the extension in either message as unsolicited and aborts with an unsupported_extension alert (Section 4.3 of [RFC9846]). A server that selects a KDF of this document MUST send the extension in its ServerHello, so the selection is covered by the transcript (Section 16.2).¶

A server that sends a HelloRetryRequest and selects a KDF of this document MUST carry the selected KDF as a schedule_profile extension in the HelloRetryRequest. That selection pins the KDF for the rest of the handshake and is the KDF implied by the HelloRetryRequest (Section 4). The client computes its second ClientHello and every later checkpoint under that KDF, and the HelloRetryRequest is covered by the transcript. A HelloRetryRequest without the extension selects the TLS 1.3 schedule for the rest of the handshake, and the server MUST NOT then send the extension in its ServerHello. A client MUST abort the handshake with an illegal_parameter alert if the ServerHello's schedule_profile, present or absent, differs from the HelloRetryRequest's, as Section 4.2.4 of [RFC9846] requires for the cipher suite.¶

6.1. What the KDF Governs

A KDF defines every key-schedule computation of the connection, including the transcript hash (Section 3). When a KDF of this document is negotiated, the hash named by the cipher suite governs nothing in the key schedule: the transcript hash is the KDF's, and the derivations and MACs are the KDF's. The transcript hash a CertificateVerify signs (Section 4.5.2 of [RFC9846]) is also the KDF's TranscriptHash.¶

The cipher suite's name still carries that hash. A connection on TLS_AES_128_GCM_SHA256 with TLS13_TURBOSHAKE256 selected takes AES-128-GCM, its Nk and Nn, and its per-record nonce construction from the suite, and takes SHA-256 from nowhere: no part of the key schedule uses it. A connection that negotiates no KDF is unaffected: the suite's hash governs its schedule exactly as TLS 1.3 specifies.¶

7. The Deck Schedule

Both KDFs of this document express the key schedule as a deck function (Section 1.3).¶

The schedule's normative interface is defined here, in terms of the profile's XOF and nothing else: Init and Absorb build a framed input sequence, Derive reads one to produce a keyed output, DeriveN reads one to produce an ordered tuple, and Ratchet crosses a stage boundary. Each Derive or DeriveN is one XOF call over its input sequence. Section 8 and Section 9 each give a short instantiation naming the profile's XOF, permutation, and domain-separation constants.¶

This document uses the following terms.¶

schedule_label:

The fixed 6-octet ASCII string "tls13 " (with a trailing space), framed at Init (Section 7.1) into every derivation of both profiles, or "dtls13" on a DTLS 1.3 connection (Section 14.1). It marks the deck schedule and is identical for both profiles, which are separated by their XOF, not by this label. It is byte-identical to the label prefix of HKDF-Expand-Label, "tls13 " in Section 7.1 of [RFC9846] and "dtls13" in Section 5.9 of [RFC9147]. Its byte-level separation from other uses of the same XOF, including the transcript hash, is covered in Section 16.8.¶

deck function:

An extendable-output function evaluated over a sequence of framed input strings, with the output length bound into the sequence before any output is produced (Section 7.1). The construction beneath it is an XOF and takes no key parameter, its secrets being ordinary framed inputs. Related keyed-sponge results are discussed in Section 16.9.¶

stage:

One of the three phases of the schedule: early (keyed by the PSK), handshake (adds the key-exchange secrets), and application. Stages are separated by ratchets (Section 7.1). A key update is a derivation of the retained traffic secret (Section 5.4), not a ratchet.¶

ratchet:

Replacing a stage's deck with a fresh deck seeded by a residue squeezed from it under "drv", then destroying the old deck (Section 16.7). Section 7.4 gives the call that produces each residue.¶

The presentation is stateful, but the construction is not. Each Derive or DeriveN equals one invocation of a profile's deck function over its framed input sequence. The three stages of Section 7.4 are protocol phases separated by stage boundaries, not KDF steps: shared trunks absorb each input once, the two squeezed residues connect the stages, and the one-way truncations fall at the stage boundaries where TLS must erase prior state. Their one-wayness is conditional (Section 16.7).¶

7.1. The Deck Schedule Interface

A deck is a running sequence of framed inputs. The profile's DF(S, L) is the XOF over that sequence (Section 8.1, Section 9.1). It returns L octets, and L is from 1 to 65535, since TurboSHAKE256 is defined only for a positive output length ([RFC9861]). The schedule runs one deck per stage, driven by five operations.¶

7.1.1. Operations 

Init([seed])         D = frame(schedule_label)
                         [ || frame("seed") || frame(seed) ]

Absorb(D, tag, v)    D = D || frame(tag) || frame(v)

Derive(D, label,     out = DF(D [ || frame(ctag) || frame(context) ]
       [context], [L])         || frame(label)
                               || frame("out_") || frame(uint16(L)), L)
                     # D is cloned, not consumed
                     # ctag names context, as tag names v in Absorb
                     # omitted L is SecretLen

(o_1, ..., o_k) =
    DeriveN(D, [(label_1, L_1),
                ...,
                (label_k, L_k)], [context])

    S = D [ || frame(ctag) || frame(context) ]
          || frame("outs") || frame(uint16(k))
          || frame(label_1) || frame("out_") || frame(uint16(L_1))
          || ...
          || frame(label_k) || frame("out_") || frame(uint16(L_k))

    o_1 || ... || o_k = DF(S, L_1 + ... + L_k)

Ratchet(D)           residue = Derive(D, "drv")
                     return Init(residue)
                     # analogue of Derive-Secret(., "derived", "")
                     # the next deck is Init, seeded with the residue
¶

Each descriptor is framed in the listed order. Each o_i is the next L_i octets of the squeezed string. The output tuple and descriptor list use the notation of Section 5.1, with the optional context last.¶

Init starts a deck by framing schedule_label. Every deck is Init'd, so every keyed sequence opens with frame(schedule_label), the label prefix of TLS 1.3 or DTLS 1.3 (Section 16.8). A ratchet residue or a retained secret is passed to Init as the seed and framed under the tag "seed" (Section 7.4, Section 5.1). Absorb feeds one tagged input into the running deck. That is the same role HKDF-Extract's mixing step plays in TLS 1.3.¶

"outs" is a fixed DeriveN terminal marker alongside "out_".¶

Derive is the single-output operation. It clones the running deck, absorbs that leaf's context, then adds the leaf label. The deck being derived from fixes ctag: a live stage trunk takes "th__", whose context is a transcript checkpoint, and a deck seeded from a retained secret takes "ctx_", whose context is that derivation's expansion context. A Derive with no context frames neither. The context precedes the label here, the reverse of TLS 1.3's HkdfLabel order. The framing is injective either way, and placing the context first lets sibling leaves that share it branch after one absorption.¶

The clone leaves the deck unchanged, so one deck yields all of a stage's leaves. Derive fills exactly HKDF-Expand-Label's role. At a stage leaf it stands in for TLS 1.3's Derive-Secret(secret, label, Messages), with the deck in place of the secret. A value keyed by a retained secret is a Derive or DeriveN over a deck seeded with that secret (Section 5.1). A Derive that omits L, including the Ratchet residue, outputs SecretLen octets. A Derive that fixes its own length passes L explicitly (the early key_block, sn_key, exporters, the ECH confirmation, MAC). When the context is omitted, L is the third argument.¶

DeriveN also clones the deck without consuming it, and uses the same context rules. Every DeriveN label MUST be registered, and labels within a descriptor list MUST be distinct. DeriveN MUST reject k outside 2..65535, any L_i outside 1..65535, or a sum above 65535. Lengths and their sum are checked before conversion to uint16, without wraparound. The count, labels, order, and each length are absorbed before squeezing. The total is determined by the length list. Binding only that total would not bind the partition.¶

DeriveN is restricted to the fixed derivations of this document. A caller MUST NOT omit, reorder, append, or resize descriptors according to which outputs it currently needs. Each derivation fixes the context and parent deck as well as the descriptors. Other protocols use Derive under Section 14.¶

Ratchet crosses a stage boundary. Its residue is a Derive under the label "drv", which is this schedule's analogue of TLS 1.3's Derive-Secret(., "derived", "") between stages. The next deck is Init'd like any other, framing schedule_label, then seeded with that residue, so "drv" names the residue, not the new deck. The residue is internal and never leaves the schedule. Any stage input, such as the asymmetric shared secret, is a later Absorb into the new deck, not part of the ratchet.¶

Section 7.4 says which boundaries use Ratchet.¶

The old deck is retired: nothing absorbs into it or derives from it afterward. This is not the in-place Ratchet() of Cyclist or STROBE ([XOODYAK], [STROBE]), which returns nothing.¶

A Derive is one DF call over its framed path, and a ratchet residue is one such Derive. It is therefore byte-exact and testable alone.¶

7.2. Labels and Alignment

schedule_label is 6 octets and every tag is 4 octets, so frame(schedule_label) fills 8 octets and every framed tag, together with the two-octet length of the value it names, fills 8 more. A value framed under a tag therefore starts on an 8-octet boundary whenever every value before it in the deck input is a multiple of 8 octets long, which lets an implementation that absorbs 64-bit lanes take key material without realigning it. With the 64-octet secrets and transcript hashes of this document, that holds for the PSK and every seed, at offset 16, for the first asymmetric shared secret component, at offset 88, for every transcript checkpoint and MAC message that follows only such values, and for the context of the ECH confirmations, at offset 56.¶

It does not hold after a value whose length is not a multiple of 8. A P-521 shared secret is 66 octets, so the transcript checkpoint after it starts at offset 162, and an external PSK has arbitrary length, so the context of its import derivation may be unaligned. In the exporter (Section 5.6), the raw label in the first Derive and the context hash in the second each start at offset 88: 8 octets for frame(schedule_label), 72 for the tagged seed, and 8 for frame("ctx_") and the context's length.¶

Every derivation label is 3 octets, and every one is registered in the TLS XOF Key Schedule Labels registry (Section 15.3), which keeps labels distinct. The tags and schedule_label are fixed by this document and are not registered. In single-output Derive a label is the last item before the output length, so its length does not bear on alignment. A short label keeps the tail of a Derive at 15 octets. In DeriveN each label precedes its own output-length field. The "outs" marker and framed count occupy 10 octets, followed by k 15-octet descriptors, for a tail of 10 + 15*k octets. Labels and tags are absorbed as they are. Apart from handshake transcript hashes, the only inputs reduced by TranscriptHash before framing are the exporter context and the ImportedIdentity, whose lengths are not bounded by this document (Section 5.6, Section 5.8).¶

7.3. Derivation Shapes

Every derivation this document replaces is an instance of one of six shapes.¶

  1. Root absorb: the Early Secret extract, as Init + Absorb.¶

  2. Accumulate: the Handshake Secret extract IKM, per component, as Absorb.¶

  3. Ratchet: Derive-Secret(., "derived", "") at a boundary, as Ratchet, or with a PSK as the "drv" output derived alongside binder_key.¶

  4. Deck derive: traffic and exporter secrets, PSK binder keys, as Derive or DeriveN.¶

  5. Secret derive: record keys, exporter label secrets and outputs, key update, resumption, PSK import ([RFC9258]), the DTLS 1.3 sequence-number key, and the ECH acceptance confirmations, as Derive or DeriveN.¶

  6. Keyed check: Finished and PSK binders, including an Exported Authenticator's Finished, as MAC.¶

Shapes 1 through 3 act on the trunk of a stage. Shapes 4 and 5 are the output operations, Derive and DeriveN, over a live trunk or over a seeded deck rooted at a retained secret (Section 5.1). Shape 6 is shape 5 under the label "mac", with the message as context (Section 5.2). Record keys are derived from their traffic secret by a separate call, as in TLS 1.3, so a retained traffic secret suffices to re-derive its keys. Deriving them within the call that produces the traffic secret would save a few invocations but break that re-derivability, so the schedule keeps the separate call.¶

7.4. Key Schedule

The schedule has three stages separated by two stage boundaries. A key-update generation is a derivation of the retained traffic secret (Section 5.4), not a further ratchet. Stage trunks and stage secrets bind no cipher suite value, matching the TLS 1.3 extracts they replace. No leaf derivation binds one directly either. A client offering several cipher suites under one KDF computes one schedule. Only record-key derivations depend directly on the suite, through Nk and Nn (Section 5.3). Every derivation frames schedule_label at Init (Section 7.1). The negotiated KDF is bound by the XOF, not by this label. This listing is identical for both profiles. Only each profile's DF instantiation differs (Section 8, Section 9).¶

E = Init()
Absorb(E, "psk_", PSK)             # "" when no PSK is selected

# early-stage leaves, each a clone of the early deck E
(binder_key, early_residue) =                  # with a PSK
    DeriveN(E, [(binder_label, SecretLen),
                ("drv",        SecretLen)])
(c_e_traffic, early_exporter_secret) =                  # 0-RTT
    DeriveN(E, [("cet", SecretLen),
                ("ees", SecretLen)], TH_CH)

H = Init(early_residue)            # without a PSK, H = Ratchet(E)
Absorb(H, "shs_", shared_secret)  # once per key-exchange component

# handshake-stage leaves, each a clone of H
(c_hs_traffic, s_hs_traffic) =
    DeriveN(H, [("cht", SecretLen),
                ("sht", SecretLen)], TH_SH)

T = Ratchet(H)                     # residue = Derive(H, "drv")
                                   # then T = Init(residue)

# application-stage leaves, each a clone of T
(c_ap_traffic, s_ap_traffic, exporter_secret) =
    DeriveN(T, [("cat", SecretLen),
                ("sat", SecretLen),
                ("exs", SecretLen)], TH_SF)
resumption_secret = Derive(T, "rss", TH_CF)
# T destroyed
¶

With a PSK, early_residue is the "drv" output of the DeriveN on E that also derives binder_key, and both peers MUST seed the handshake deck with it rather than with a residue of Ratchet(E), which would differ. Without a PSK, both early DeriveN calls are omitted and H = Ratchet(E). The handshake boundary always uses Ratchet(H). The DeriveN that derives c_e_traffic and early_exporter_secret is used for 0-RTT. At the early-to-handshake boundary, E and early_residue are destroyed after H is initialized. The handshake boundary destroys H and its residue after T is initialized. A PSK-only handshake omits the Absorb into H.¶

binder_label is selected as specified in Section 5.5. early_residue is retained until the early boundary. The early traffic and exporter DeriveN uses TH_CH even if only one of its outputs is needed.¶

When the negotiated group is a hybrid or other multi-component key exchange, shared_secret denotes the ordered list of component shared secrets whose concatenation the group specification defines as its shared secret (for example, [RFC9954]). Both peers MUST use exactly those components in that concatenation order, absorbing each with its own Absorb(H, "shs_", component), without first concatenating them.¶

7.4.1. Absent and Empty Inputs

A handshake without a PSK still executes Absorb(E, "psk_", ""). That call contributes the following bytes:¶

frame("psk_") = 0x0004 || "psk_"
frame("")     = 0x0000
¶

This is unambiguous because a PSK of this document is never zero-length: an imported or resumption PSK is 64 octets (Section 10), and an endpoint MUST NOT use an empty raw external PSK. Without a PSK, the early stage carries no leaves and its deck holds only known constants, as TLS 1.3's Early Secret is the extract of two known constants. The stage exists for uniformity across handshake modes, and the schedule's security does not rest on its secrecy when no PSK is present. A PSK-only handshake omits Absorb(H, "shs_", ...) entirely: the tag "shs_" does not appear in the sequence.¶

7.4.2. Stage Secrets

The three stage decks E, H, and T are this schedule's analogue of TLS 1.3's Early, Handshake, and Main Secret. They are states, not values. A leaf clones the running deck rather than reading an extracted octet string, so no named early or main secret is materialized.¶

Each stage boundary seeds the next deck with a residue under "drv" (Section 7.4), and that deck frames schedule_label at Init. That residue is the analogue of TLS 1.3's unnamed "derived" salt. It never leaves the schedule. It seeds the next deck once and is then discarded (Section 16.7).¶

The values that do leave, the traffic and exporter secrets, occupy disjoint slices within a DeriveN output tuple. The DeriveN calls that derive early, handshake, and application traffic and exporter secrets each bind their ordered labels, lengths, and transcript checkpoint (Section 16.8). Early data is separated in addition by the 0-RTT equality check (Section 4). Every stage binds its transcript at the leaves, so the decks themselves bind none. The derivation graph maps onto the TLS 1.3 graph (Section 16.6.3).¶

8. The TLS13_TURBOSHAKE256 Profile

The TLS13_TURBOSHAKE256 profile instantiates the deck schedule of Section 7 with TurboSHAKE256 [RFC9861], built on the 12-round Keccak-p[1600,12] permutation of [FIPS202].¶

The profile parameters are:¶

SecretLen:

64 octets, the length of every stage and traffic secret.¶

FLen:

64 octets.¶

8.1. Instantiation

The deck function is:¶

DF(S, L) = TurboSHAKE256(seq(S), 0x1F, L)
¶

where seq(S) is the concatenation of every framed item of S in order. TurboSHAKE256's output length is in octets per [RFC9861], so L is passed unchanged, unlike the SHAKE256 profile, whose bit-oriented length needs an 8 * L conversion (Section 9.1).¶

The transcript hash of Section 2.1 is instantiated with the same function: TranscriptHash(x) = TurboSHAKE256("tls13 hash" || x, 0x1F, 64). The domain-separation byte is fixed to 0x1F, the default of [RFC9861], for every use of TurboSHAKE256 in this profile, so an API without the D parameter implements the profile unchanged.¶

TurboSHAKE256 uses the Keccak-p[1600,12] permutation as a sponge: input is absorbed into a 1600-bit state in rate-sized blocks of 136 octets, with the permutation applied after each block, and output is read from the same state. The capacity is the 512-bit portion of the state that input and output never touch. It is what the erasure argument of Section 16.7 relies on, and the 64-octet secret, transcript-hash, and Finished and binder MAC lengths are set to match it.¶

8.1.1. Required API Surface

The required API surface is incremental absorption, cloning of an unfinalized state, and one-shot squeeze with the output length known up front. Cloning before any output is incremental input to two separate invocations, which Section 2.1 of [RFC9861] permits. No absorb-after-squeeze occurs anywhere in this document, so no access below the TurboSHAKE interface is required. The clone discipline is the same one TLS stacks already apply to SHA-2 transcript-hash checkpoints.¶

9. The TLS13_SHAKE256 Profile

The TLS13_SHAKE256 profile instantiates the deck schedule of Section 7 with plain SHAKE256 [FIPS202], built on the 24-round Keccak-f[1600] permutation, in place of TurboSHAKE256's Keccak-p[1600,12]. This profile mirrors the TLS13_TURBOSHAKE256 profile's framing exactly: domain separation comes from the same framed-prefix mechanism the TurboSHAKE profile uses, an absorbed frame(schedule_label) at Init (Section 7.1), not from cSHAKE's function-name and customization-string inputs. The two profiles' decks therefore differ only in the underlying permutation, so derivation (Section 5.1) and the MAC construction (Section 5.2) are shared by both profiles.¶

The profile parameters, SecretLen and FLen, are 64 octets as in Section 8.¶

9.1. Instantiation

The deck function is:¶

DF(S, L) = SHAKE256(seq(S), 8 * L)
¶

where seq(S) is the concatenation of every framed item of S in order, SHAKE256(X, L) is the function of [FIPS202] with X the main input and L the output length in bits, and 8 * L converts this document's octet-oriented L to the bit-oriented L argument of SHAKE256.¶

SHAKE256 takes no function-name or customization-string input. This profile's domain separation comes from seq(S) beginning with frame(schedule_label), as Section 9 describes (Section 7.1).¶

The transcript hash of Section 2.1 is instantiated with the same function: TranscriptHash(x) = SHAKE256("tls13 hash" || x, 512).¶

SHAKE256 uses the Keccak-f[1600] permutation as a sponge with the same 136-octet rate and 512-bit capacity as TurboSHAKE256 (Section 8.1). The capacity is what the erasure argument of Section 16.7 relies on, and the 64-octet secret, transcript-hash, and Finished and binder MAC lengths match it in both profiles.¶

9.1.1. Required API Surface

The required API surface is that of Section 8.1: no absorb-after-squeeze occurs, so no access below the SHAKE256 interface is required.¶

10. PSK Importer

TLS 1.3 permits external PSKs [RFC9846], and [RFC9258] imports an external PSK into a target KDF, producing a PSK bound to its target. This document updates the importer computation in Section 5.1 of [RFC9258] for the KDFs defined here. It replaces HKDF-Extract and HKDF-Expand-Label using the EPSK-associated hash, or its SHA-256 default, with the target KDF's "ipk" derivation and TranscriptHash (Section 5.8). [RFC9258] uses the target KDF only for output length and identity separation. This document also uses it to select the importer computation, avoiding a SHA-2 dependency.¶

A provisioning importer taught only the new TLS KDF Identifier and output length still applies the EPSK-associated-hash rule of [RFC9258]. It produces a different ipsk for the same ImportedIdentity than the importer specified here. A peer using this document's computation discovers the mismatch at binder verification.¶

A KDF of this document is a TLS KDF Identifier (Section 15), so an external PSK imported for use with one is imported under the unchanged ImportedIdentity of [RFC9258], with target_kdf naming the KDF. No variant structure is needed, and none is defined. For a DTLS 1.3 target, the "ipk" derivation frames "dtls13" as its schedule label, since Section 5.1 of [RFC9258] uses the label prefix of the target protocol.¶

[RFC9258] binds an imported PSK to a KDF and not to a cipher suite, deliberately, so that a PSK cannot be reused across key schedules. Negotiating the schedule in its own extension makes that KDF a value the protocol negotiates, so the binding applies as [RFC9258] intends.¶

The import derivation is the generic derivation of Section 5.8, keyed by epsk under target_kdf. An endpoint MUST NOT import an epsk, or use a raw external PSK, longer than 0xFFFF octets, so every framed value fits a single frame. A client that imports one external PSK for use under more than one KDF MUST produce a separate ImportedIdentity, and hence a separate ipsk, per target_kdf, exactly as [RFC9258] requires.¶

Import is RECOMMENDED. As in [RFC9258], it is not required. A raw external PSK is associated with its KDF when it is established. One established without a KDF is associated with SHA-256, as Section 4.3.11 of [RFC9846] specifies for an external PSK without a hash, and so with the TLS 1.3 schedule rather than a KDF of this document. A raw external PSK carries no binding to the KDF it is used under, and its length is whatever provisioning chose, so a length that is not a multiple of 8 leaves the items after it unaligned (Section 7.2) and may cost one further permutation. An imported PSK is SecretLen octets and raises neither question.¶

For imports into these KDFs, target-KDF selection also supersedes the single-associated-hash restriction in Section 4 of [RFC9258]. The separate ImportedIdentity values bind each ipsk to one target KDF, preventing reuse of one imported PSK across TLS schedules. They do not isolate the underlying epsk from the different importer KDFs: importing the same epsk for both profiles feeds that secret to both permutations (Section 16.1).¶

11. Zero-RTT and Early Data

Early data remains PSK-only and remains replayable under the TLS 1.3 anti-replay model. This document changes neither. A client MAY send early data using the first offered PSK's associated parameters (Section 4) only if they permit early data and the associated cipher suite is among those it offers. A server MUST reject early data unless the offered PSK's associated parameters permit early data, the selected cipher suite equals the offered PSK's associated cipher suite, the selected ALPN equals the PSK's associated ALPN, and all TLS 1.3 anti-replay checks pass. The suite-equality check, not the binder, prevents redirecting early data to a different AEAD.¶

12. Authentication

Certificate-based authentication is negotiated as in TLS 1.3, and what a CertificateVerify signs follows from the transcript hash. The content covered by the signature is Transcript-Hash(Handshake Context, Certificate) (Section 4.5.2 of [RFC9846]), and under a KDF of this document that is the 64-octet TranscriptHash of Section 2.1. The 64 octets of 0x20, the context string, and the separator octet are unchanged, so a server signs:¶

0x20 (64 times) || "TLS 1.3, server CertificateVerify" || 0x00
    || TranscriptHash(Handshake Context, Certificate)
¶

The signature scheme then processes that content as its own definition requires, and that processing is outside the key schedule. The ECDSA and RSASSA-PSS schemes of TLS 1.3 hash it with SHA-2, and Ed25519 uses SHA-512 internally, whatever KDF is negotiated. A certificate chain carries the same dependence through the signature schemes of its certificates, which the signature_algorithms_cert extension negotiates (Section 4.3.3 of [RFC9846]).¶

A deployment that must avoid SHA-2 entirely MUST restrict the signature_algorithms and signature_algorithms_cert extensions to signature schemes that use no SHA-2, such as Ed448 ([RFC8032]) or ML-DSA ([FIPS204], [I-D.ietf-tls-mldsa]), or use PSK-only authentication.¶

14. Companion Mechanisms

Several deployed mechanisms invoke HKDF-Expand-Label or HMAC directly. This document defines the Encrypted Client Hello confirmation for its KDFs (Section 5.7), because ECH is pervasive in the deployments most likely to exercise these schedules, defines DTLS 1.3 (Section 14.1), and updates Exported Authenticators, which use the exporter and the cipher suite's hash (Section 14.2).¶

A protocol built on TLS 1.3 that derives keys from a secret of this key schedule with HKDF-Expand-Label(Secret, Label, Context, Length) instead uses the Derive of Section 5.1 on a connection that negotiates a KDF of this document: Derive(Init(Secret), label, Context, Length), with the context omitted when it is empty. Such a protocol MUST use the single-output form. The sequence-number key of DTLS 1.3 (Section 14.1) is an instance of this rule.¶

That protocol's specification assigns the label and registers it in the TLS XOF Key Schedule Labels registry (Section 15.3), whose registration rules keep every label 3 octets long (Section 7.2) and distinct from every other label. Until its specification registers its labels, such a protocol has no defined derivation under this key schedule.¶

Any other mechanism that derives keys with HKDF-Expand-Label or HMAC, including one that derives them before any KDF is negotiated, is not covered by this document and needs its own specification.¶

Until a specification defines a mechanism's derivations for a KDF of this document, an endpoint that negotiates that KDF MUST NOT use the mechanism on that connection. QUIC [RFC9001] has no such specification yet: its "quic key", "quic iv", "quic hp", and "quic ku" labels are not registered (Section 15.3), and its Initial secrets are derived before any KDF is negotiated. An endpoint MUST NOT negotiate a KDF of this document in QUIC until one exists.¶

14.1. DTLS 1.3

DTLS 1.3 [RFC9147] uses the key schedule of TLS 1.3 with two changes, and a KDF of this document applies both. This document updates [RFC9147] for a connection that negotiates a KDF of this document. A connection that negotiates no KDF uses [RFC9147] unchanged.¶

First, Section 5.9 of [RFC9147] replaces the "tls13 " label prefix with "dtls13" to separate DTLS 1.3 keys from TLS 1.3 keys. schedule_label is that prefix (Section 7), so a DTLS 1.3 connection frames "dtls13" at every Init:¶

frame(schedule_label) = 0x0006 || "dtls13"
¶

Every DTLS 1.3 derivation therefore has a different input from the TLS 1.3 derivation over the same values. The transcript hash is unchanged: its "tls13 hash" prefix separates it from keyed sequences (Section 16.8) and is not a label prefix, and DTLS 1.3 computes the transcript over the messages that Section 5.2 of [RFC9147] specifies.¶

Second, Section 4.2.3 of [RFC9147] derives a key for record sequence number encryption from each traffic secret. It is a derivation of that secret, alongside the record keys of Section 5.3:¶

sn_key = Derive(Init(traffic_secret), "snk", Nk)
¶

Nk is the AEAD key length, the key_length of [RFC9147].¶

For DTLS 1.3, a sender MUST remain able to send in the original epoch while handshake retransmission and acknowledgement obligations require it, including until the final flight is acknowledged (Section 4.2.1 of [RFC9147] and Section 7.1 of [RFC9147]), and MUST continue advancing that epoch's send record sequence number without resetting it. It can keep the epoch's record key, IV, and sn_key, or re-derive them from a retained traffic secret: key_block is deterministic, so both give the same keys.¶

Because key_block is deterministic, re-deriving it and resetting the sequence number repeats the record key and nonce. With AES-GCM, nonce reuse across different records permits recovery of the GHASH authentication subkey and record forgery through Joux's forbidden attack [JOUX], demonstrated against TLS by [NONCE-DISRESPECT].¶

14.2. Exported Authenticators

Exported Authenticators [RFC9261] let either peer authenticate after the handshake. [RFC9261] computes each authenticator from two exporter values and an "authenticator hash", which it defines as the hash associated with the cipher suite (Section 5.1 of [RFC9261]). Under a KDF of this document the cipher suite's hash governs nothing (Section 6.1), so this document updates [RFC9261] for a connection that negotiates a KDF of this document. A connection that negotiates no KDF uses [RFC9261] unchanged.¶

The authenticator hash is the KDF's TranscriptHash (Section 2.1), and its output length is 64 octets. The Handshake Context and the Finished MAC Key of Section 5.1 of [RFC9261] are values of the TLS-Exporter of Section 5.6, keyed by exporter_secret, with the labels [RFC9261] registers, an empty context, and a length of 64 octets. For an authenticator sent by the server:¶

HC = TLS-Exporter(
       "EXPORTER-server authenticator handshake context", "", 64)
FK = TLS-Exporter(
       "EXPORTER-server authenticator finished key", "", 64)
¶

A client uses the "EXPORTER-client" labels in the same way. The CertificateVerify of Section 5.2.2 of [RFC9261] signs the octet 0x20 repeated 64 times, the context string "Exported Authenticator", a zero octet, and:¶

TranscriptHash(HC || authenticator request || Certificate)
¶

The Finished of Section 5.2.3 of [RFC9261] is the MAC of Section 5.2 in place of HMAC, with FLen, which is 64:¶

Finished = MAC(FK,
               TranscriptHash(HC || authenticator request
                              || Certificate || CertificateVerify),
               FLen)
¶

The Finished of an empty authenticator (Section 6 of [RFC9261]) is the same computation with no CertificateVerify, over a Certificate message that carries the certificate_request_context of the authenticator request and no CertificateEntries. That Certificate message is serialized and hashed like any other but is not sent, and it is not a zero-length string. As in [RFC9261], an absent authenticator request contributes no octets.¶

Every other rule of [RFC9261] applies unchanged, including the use of exporter_secret and not early_exporter_secret, the uniqueness of certificate_request_context, and the requirement that a server verify the client Finished before sending or processing an authenticator. The signature scheme keeps its own hash, as Section 12 describes.¶

On a DTLS 1.3 connection, exporter_secret, the exporter outputs, and the Finished MAC all use schedule_label "dtls13" (Section 14.1).¶

An implementation of Exported Authenticators outside the TLS library (Section 7.3 of [RFC9261]) MUST obtain the connection's negotiated KDF identifier, or an indication that no KDF was negotiated, and whether the connection uses TLS or DTLS. The KDF selection determines the authenticator hash and MAC, their output lengths, and the exporter output lengths. The protocol determines the MAC's schedule_label. An API providing only TLS-Exporter(label, context, length) is insufficient because it does not convey that selection. Updating the TLS library alone can therefore leave an application producing incompatible authenticators.¶

16. Security Considerations

16.1. KDF Separation

TLS13_TURBOSHAKE256 and TLS13_SHAKE256 frame the same schedule_label, so their inputs can coincide. They run different permutations, the 12-round Keccak-p[1600,12] and the 24-round Keccak-f[1600], though the first is the last 12 rounds of the second ([FIPS202], Sections 3.3 and 3.4). Most secret inputs are bound to a single KDF (Section 4). For those secrets, coincident framed inputs do not by themselves expose either secret if both XOFs jointly behave as independent random oracles and the source-secrecy premises hold (Section 16.6).¶

An external PSK used under both profiles is the exception. For an imported PSK, Section 10 requires a separate ipsk per target_kdf, but the epsk beneath them is one secret, absorbed under both permutations. Raw external PSK reuse also shares a secret between profiles. A deployment that negotiates TLS13_SHAKE256 to avoid the reduced-round premise (Section 16.10.1) does not gain that separation for such a PSK. A deployment that provisions a separate external PSK per KDF, rather than using one under both, has no secret in common between them.¶

16.2. Downgrade Resistance

The selected cipher suite appears in the ServerHello and therefore in the transcript from TH_SH onward, which every handshake and application output binds (Section 7.4). A peer that assumed a different suite would hold a different transcript, and its Finished MAC would fail.¶

Stripping the extension in flight makes the ClientHello transcripts differ and the Finished MACs fail. A server can decline the extension by omitting it from the ServerHello (Section 6). The client decides whether to accept that capability mismatch. A deployment that offers both KDFs accepts whichever the server echoes.¶

16.3. PSK Entropy

An attacker who can guess an external PSK can recompute its binder offline. External PSKs SHOULD be drawn with at least 512 bits of entropy, a conservative recommendation that bounds guessing in the random-oracle game by q / 2^512 in q queries (Section 16.6). The 512-bit capacity sets a 256-bit security target, rather than requiring 512 bits of PSK entropy.¶

16.4. Authentication

A fully SHA-2-free connection also needs SHA-2-free authentication, which Section 12 specifies.¶

The exporter labels that Exported Authenticators use are registered, not reserved, so an application with access to the exporter can obtain the Finished MAC Key (Section 14.2).¶

16.5. Hybrid Key Exchange

One high-entropy component keeps the derivation unpredictable even if another is adversarial. This robustness relies on injective framing and the random-oracle argument (Section 16.8, Section 16.6, [BINDEL]), and on the source-secrecy and cross-stage simulation conditions left open in Section 16.6.4.¶

16.6. Cryptographic Analysis

The per-derivation bound comes from the sponge analysis ([BDPV08]), assuming source secrecy and the composition below. Protocol security also depends on erasure and authentication, with proof obligations still open (Section 16.6.4).¶

16.6.1. Threat Model and Goals

The adversary model and key-schedule goals are those of [TLS13KS]: an active network adversary controls message delivery. It may learn selected stage secrets under compromise predicates. Authentication of peer identity remains outside the cipher suite, as in TLS 1.3. The schedule must provide indistinguishability of record keys and exporter outputs under the chosen AEAD, integrity of the handshake transcript through Finished and binder verification, forward secrecy from compromise of a handshake traffic secret to application traffic once the asymmetric shared secret is used, and the TLS 1.3 0-RTT replay model when early data is accepted.¶

16.6.2. Primitive Assumptions

DF is the profile's XOF over a framed byte string, its permutation modeled as random ([FIPS202]). A sponge over such a permutation is indifferentiable from a random oracle up to 2^(c/2) of its calls ([BDPV08], Theorem 2 and Section 5), which is 2^256 at the 512-bit capacity both profiles use.¶

The step from sponge to oracle is the indifferentiability composition of [MRH], which is sound for single-stage games and not in general for multi-stage ones ([RSS]).¶

Every Derive or DeriveN is a single call DF(S, L) where seq(S) is injectively framed (Section 16.8), so calls with different inputs query the oracle at different points, and the outputs of one DeriveN are disjoint slices of one answer. In the random-oracle game, an adversary that never queries a string carrying the secret cannot distinguish those outputs from independent uniform strings. For a secret with 512 bits of entropy conditioned on its view, the chance of such a query is at most q / 2^512 in q queries (Section 16.3 covers a weaker external PSK). These are bounds in that game, subject to the preceding composition step, not bounds for the complete protocol.¶

If the DeriveN answer is uniform, revealing some slices leaves the others uniform and independent, provided the adversary has not queried the secret-bearing input and has learned neither the full output tuple, nor a secret the tuple was derived from, nor another name for a target slice. Real outputs are not uniform strings, so carrying this over to them needs a joint pseudorandomness assumption, or a completed game and simulation, together with their losses (Section 16.6.4).¶

Finished and binder verification require MAC to be unforgeable under a chosen-message attack. Each MAC key is a 64-octet finished_key used for MAC and nothing else (Section 5.5). The same key may be used over several messages, as for a binder recomputed after a HelloRetryRequest or for post-handshake Finished messages within one traffic generation.¶

For Exported Authenticators, the MAC key is the 64-octet Finished MAC Key, also used for MAC and nothing else. The same key can serve successive Exported Authenticators on one connection (Section 14.2).¶

MAC is a Derive (Section 5.2), so the preceding random-oracle argument applies. In that game, a uniform secret unknown to the adversary keys a pseudorandom function of the rest of the framed input. With an L-octet output, each verification attempt adds at most 2^(-8L) to the forgery probability, in addition to the probability of querying the secret.¶

The uniformity of finished_key to an adversary depends on that of the secrets beneath it. A finished_key derived from a guessable external PSK is not uniform to the adversary (Section 16.3).¶

If the ECH confirmation Derive output (Section 5.7) is pseudorandom, a network attacker without ClientHelloInner.random guesses the 8 octets with probability at most 2^-64 per attempt, plus its advantage in distinguishing the output from random.¶

16.6.3. Derivation Graph

The stage trunks E, H, and T and the ratchet residues map to TLS 1.3's Early/Handshake/Main Secrets and its unnamed "derived" salt as Section 7.4.2 sets out. DeriveN also combines sibling sites into one query. The map is onto rather than one to one: this document derives key_block once and slices the record key and IV from it, where TLS 1.3 derives each at its own site. It is structural and does not carry the TLS 1.3 proof.¶

16.6.4. What Is Not Yet Established

This schedule does not yet have an analysis equivalent to [TLS13KS].¶

The single-stage classification needed for [MRH]'s composition remains unproved ([RSS], Section 16.6).¶

[TLS13KS] is proved over discrete extract-and-expand nodes, not over an accumulator carried across each stage and cloned at its leaves. The cross-stage chaining needs analysis, in particular absorbing the asymmetric shared secret into a deck seeded with the early residue, the step TLS 1.3 performs as an HKDF-Extract salted with the early secret's "derived" value.¶

For DeriveN, that analysis must also cover joint outputs, selective disclosure, and the exposure changes caused by materializing and erasing output tuples.¶

Whether the ECH confirmation replacement (Section 5.7) keeps every property [RFC9849] analyzes is not established here.¶

16.7. Erasure Boundaries

A sponge accumulator is built on a permutation, and permutations are invertible. If the intervening absorbed blocks are known, anyone holding a later state can recover the earlier one. Carrying a raw accumulator across a stage boundary would therefore let a post-handshake state compromise re-derive handshake traffic secrets when those intervening blocks are known.¶

A Ratchet breaks the chain because its squeeze returns a function of the state, not the state itself. In the random-oracle game ([MRH]), recovering it requires a query on the secret-bearing input. A boundary mixing an asymmetric shared_secret relies instead on the exchange's computational hardness and the open chaining analysis (Section 16.6.4), not on information-theoretic entropy given the public key shares. The early-to-handshake boundary carries only the PSK, so its one-wayness depends on the PSK's min-entropy (Section 16.3): a low-entropy external PSK earns no forward secrecy there from that boundary alone. A PSK-only handshake absorbs no asymmetric shared secret at all (Section 7.4.1), so every boundary has the same PSK-entropy limitation.¶

The one-wayness argument is conditional on erasing the old trunk. The squeeze does not erase it.¶

A ratchet's forward secrecy is only as good as the erasure behind it, and erasure is local: no peer observes it, and no interoperability test detects its absence. The erasure rules below are therefore expectations, not interoperability requirements, and an implementation SHOULD follow them as its platform allows.¶

An accumulator of a stage should not outlive that stage's ratchet, should not be retained as a successor across a ratchet, and should not be serialized, exported, or compared. Handshake-stage traffic secrets and record keys should be destroyed when their TLS 1.3 analogues would be, and each stage secret once the next stage has absorbed it.¶

For DTLS, destruction of epoch material is subject to the retention requirements in Section 14.1.¶

Every cloned accumulator is a 200-octet copy of secret state, and a clone exists for the span of a Derive or DeriveN. Keeping that window short, and zeroizing each clone when it is dropped, limits what a compromise recovers. A buffer holding the complete output tuple of a DeriveN that derives record keys exposes both its record material and its finished_key or successor secret. Redundant buffers holding DeriveN output tuples should be erased after their slices have been distributed. Unused successor secrets should be erased when the connection closes, subject to the DTLS retention rules above. Compromise of a live accumulator yields that stage's underived leaves, as compromise of a stage secret does in TLS 1.3. With the preceding state and other absorbed blocks known, invertibility can also expose an absorbed asymmetric shared secret.¶

On platforms that cannot guarantee erasure these erasure rules are best effort (Appendix C).¶

16.8. Domain Separation

Distinct derivation paths yield distinct byte strings as deck-function inputs. A framed sequence decodes to exactly one list of items: frame(x) is uint16(len(x)) || x with no padding (Section 2).¶

Every deck opens with frame(schedule_label), then its rooting item (Section 7.1, Section 5.1): the PSK for the early stage, the early residue for the handshake stage, the handshake residue for the application stage, and the retained secret for a derivation (Section 7.4). The PSK is framed under the tag "psk_" and every residue or retained secret under "seed", so the early trunk differs from every other deck in its first tag. Decks that open with the same tag are told apart by their seed value and not by their structure. A path over a live stage trunk and a path over a deck seeded with a retained secret draw from disjoint label vocabularies (Section 7.4, Section 7.2). Within either, every item before the terminal label or the "outs" marker is a framed tag drawn from this document's fixed vocabulary followed by its framed value, in an order the schedule fixes, so two paths of the same kind and the same length that agree tag for tag can differ only in a value. Two paths that differ at all therefore differ at some item, so their framed sequences differ. The "outs" marker cannot be a prefix tag or a three-octet Derive label, so it separates DeriveN from both a Derive and an unfinished prefix. Its framed descriptor count fixes how many labels and lengths follow, and those ordered lengths fix the DeriveN output partition.¶

Unkeyed transcript hashing is separated at the byte level:¶

"tls13 hash"           = 0x74 0x6c ...

frame(schedule_label)  = uint16(6) || "tls13 "
                       = 0x00 0x06 || "tls13 "
¶

The first octet separates a keyed sequence from the transcript hash.¶

16.9. Related Constructions

An HKDF schedule over a SHA-3 hash would keep the analysis of [TLS13KS] applicable. A proof that Derive and DeriveN are jointly pseudorandom, over many keys, would discharge the pseudorandomness assumptions [TLS13KS] makes of its expand function and of the MAC deriving its binder values, though not its extraction, collision-resistance or salted Diffie-Hellman assumptions. No keyed-sponge result reaches this construction as specified. The outer-keyed sponge is Sponge(K || m), the key first, with the analysis limited to keys occupying whole rate blocks ([KEYEDSPONGE]), where this schedule frames schedule_label ahead of a framed secret that does not fill a rate block. Closing this needs a keyed-sponge result that tolerates a public prefix and a secret that does not fill a block, or a schedule that fits an existing one.¶

Appendix B. Permutation-Counting Method

This appendix is non-normative.¶

For an input of n octets producing L octets, a sponge over the profile's permutation applies floor(n / 136) + 1 permutations while absorbing, since the padding rule always appends at least one octet, and ceil(L / 136) - 1 more while squeezing, since the first output block is read from the state the absorption left.¶

For DeriveN, L is the sum of all descriptor lengths. The 192-octet output tuple of the DeriveN that derives c_ap_traffic, s_ap_traffic, and exporter_secret therefore needs one extra squeeze block.¶

A DeriveN call absorbs its checkpoint once for all its slices. The siblings that shared a context in the single-output baseline are now slices of that one call. Summing the standalone cost floor(n / 136) + 1 + ceil(L / 136) - 1 for each of the 15 calls gives 23 permutations. Sharing absorption between calls does not change this total for the stated workload.¶

Each HKDF-Extract, and each HKDF-Expand-Label of at most 32 octets, is one HMAC-SHA3-256, and one HMAC-SHA3-256 is four permutation calls: two for the inner hash of (K XOR ipad) || m and two for the outer hash of (K XOR opad) || digest, each filling one 136-octet block and padding into a second.¶

Appendix C. Implementation Considerations

This appendix is non-normative.¶

Both profiles need the same three capabilities of an XOF: incremental absorption, cloning of a state that has not produced output, and a squeeze of a length known before the squeeze begins. Each profile's concrete parameters are in Section 8.1 and Section 9.1.¶

Each handshake and application leaf absorbs its transcript checkpoint, TH_SH, TH_SF, or TH_CF, as its context (Section 7.4), the same point at which the corresponding TLS 1.3 Derive-Secret call consumes Messages. A stack ported from TLS 1.3 therefore need not compute any transcript checkpoint it does not already compute.¶

A client that offers PSKs associated with different KDFs computes each binder under its own PSK's KDF, and therefore maintains transcript-hash state per KDF for the partial ClientHello transcript. TranscriptHash is itself defined by the KDF (Section 8.1, Section 9.1), so the checkpoints of Section 2.1 differ per offered KDF. A client offering more than one either buffers the handshake messages until the KDF is known or carries checkpoint state per offered KDF, discarding the state of those not selected once the KDF is pinned, at the ServerHello or at a HelloRetryRequest. This is the one place where offering more than one KDF costs an implementation more than a single schedule: the schedule binds no cipher suite (Section 7.4), so it is shared across every suite offered. The suite-dependent lengths are described in Section 5.3 and Section 14.1.¶

A binder finished_key uses standalone Derive under binder_key. A handshake finished_key is the "fin" output of the DeriveN over its traffic secret that also derives the record keys. Post-handshake authentication uses standalone Derive under the current application secret (Section 5.5). Sharing the label "fin" does not make these derivations interchangeable. An implementation that feeds a binder's MAC key from the Finished path's base secret produces a wrong binder that no Finished-path test vector detects.¶

A DeriveN implementation knows the whole descriptor list before it squeezes. It can distribute slices directly to their consumers or use a temporary combined buffer. It should erase temporary state and retain only required outputs (Section 16.7). Requesting one slice does not change the DeriveN call.¶

In garbage-collected runtimes, zeroization is inherently best effort: the runtime may have copied or moved key material, and erasing every copy is not achievable from the language. The erasure rules of Section 16.7 are written to be met on such platforms by ceasing use, dropping references, and zeroizing the buffers the implementation controls, as implementations already do for TLS 1.3 key material.¶
